## 从一个朴素事实出发：代码总是在消费和产生数据

无论软件表面上提供的是页面、接口、工作流还是智能体，它的核心活动都离不开两件事：读取数据，并产生新的数据。

传统开发中，人类通常同时掌握代码、数据库、接口约定和业务背景。即使契约分散在 SQL DDL、ORM model、TypeScript 类型、校验器和文档里，人也常能凭经验把它们拼起来。这个过程代价不低，但迭代速度有限时，问题尚可被人工协调掩盖。

Agent 改变了这个前提。Agent 可以快速生成、修改并集成代码，却不会天然拥有团队成员脑中的隐含上下文。它需要从系统中直接获得三个答案：

1. 这份数据的结构是什么？
2. 这份数据在业务上是什么意思？
3. 一次写入怎样才算有效？

如果答案只能通过搜索代码、猜测命名、追查迁移记录和询问人类才能拼出，那么代码生成越快，错误契约被放大的速度也越快。对 Agent 友好的开发环境，首先需要一个对 Agent 友好的数据层。

## Agent 加速开发后，数据层成为新的瓶颈

Agent 驱动的高频迭代要求 Schema 可以持续演进，而不是在 day one 被假定为已经设计完毕。与此同时，快速变化不能以弱化契约为代价：整个数据面仍应接受强 Schema 校验，否则每一次局部改动都可能制造新的数据形态，最终产生难以识别的 Schema drift。

这里存在一个表面矛盾：

- Schema 必须足够稳定，才能可靠地约束读写；
- Schema 又必须能够演进，才能跟上业务和 Agent 的迭代速度。

nomicore 的出发点不是在“固定 Schema”和“无 Schema”之间二选一，而是让每一个时刻都存在明确、可验证的当前契约，同时让契约本身也成为可以被管理、持久化和演进的数据。

## Vibe coding 如何放大隐式 Schema 问题

先看三个在 vibe coding 中很容易出现的例子。

### 例子一：金额结构相同，语义已经分叉

最初的提示是：“给订单增加总金额，并显示为两位小数。”Agent 看到的示例只有：

```json
{
  "total": 99.9
}
```

它很自然地写出 `total.toFixed(2)`。但这个例子没有定义金额是元还是分、是否允许负数、缺失值意味着零还是错误，也没有说明浮点误差和币种。

后来，另一个 Agent 接到“接入支付平台”的任务。支付平台使用整数分，于是它开始写入：

```json
{
  "total": 9990
}
```

两个模块都认为 `total` 是 `number`，类型检查也可能全部通过，但页面会把 9990 分显示成 9990.00 元。数据结构没有变化，业务语义却已经分叉。仅靠 `number` 无法让 Agent 判断哪一方违反了契约，因为契约从未被写下来。

### 例子二：新增状态落入错误的旧分支

订单最初只有三个状态：`pending`、`paid` 和 `shipped`。Agent 根据这几个例子写出：

```ts
if (order.status === "pending") {
  showPayButton();
} else {
  showTrackingInfo();
}
```

后来，为了支持退款，另一个 Agent 增加了 `refunding` 和 `refunded`。创建退款的模块工作正常，旧页面也没有抛错，却会把两个新状态都送进 `else` 分支并显示物流信息。

系统中还可能散落着 `status !== "pending"`、`status === "paid"` 和各式默认分支。支持新状态需要改动多少位置无法预先判断；改完之后，也难以证明旧状态仍保持原行为。新输入没有被明确拒绝，而是被旧代码“成功地”处理成错误结果。

### 例子三：上游能输出，不等于下游能处理

模块 A 负责读取用户信息，最初只输出：

```json
{
  "role": "admin"
}
```

模块 B 根据角色显示删除按钮：

```ts
if (user.role === "admin") {
  showDeleteButton();
}
```

后来，Agent 为模块 A 增加了 `owner`、`editor`、`viewer` 和 `suspended`。A 的新功能看起来已经完成：它能读取并返回所有新角色。但 B 只认识 `admin`，其余值全部进入没有明确定义的默认行为。`owner` 可能失去管理能力，`suspended` 也可能被当作普通用户继续操作。

这里真正需要证明的是：

```text
模块 A 的所有可能输出 ⊆ 模块 B 的所有可处理输入
```

当两边的 Schema 都隐含在代码中时，这个包含关系无法在集成前检查。只有数据实际流入某条路径后，系统才会以错误页面、权限漏洞或偶发异常的形式给出答案。

### 从例子中可以看到什么

这三个例子分别表现为金额误读、状态误判和模块不兼容，但背后是同一个机制。

Vibe coding 常从少量例子开始。人们给 Agent 一两个典型输入，描述期望结果，然后让 Agent 据此理解需求、设计方案并编码。这种方式擅长快速建立“看起来能工作”的纵向切片，却很少同时明确三类完整契约：程序接受什么输入、产生什么输出，以及持久化什么数据。

例子只能说明少数样本应该怎样工作，不能定义整个输入空间。Agent 会根据样本和局部代码推断缺失的规则，再把推断写进分支、字段访问、默认值和异常处理之中。于是，绝大多数 Schema 没有独立定义，而是由处理代码隐式定义。

这种隐式 Schema 具有三个特点：

- **局部**：每个模块只体现自己碰巧处理过的样本和路径；
- **不可枚举**：很难通过一个入口回答完整的允许范围和拒绝范围；
- **随指令漂移**：后续提示通常只要求支持新例子，Agent 会局部修改代码，却未必同步修正所有生产者、消费者和历史数据的假设。

随着给 coding agent 的指令不断迭代，程序不同部分会从同一批初始例子出发，逐渐形成方向不同的隐式 Schema。代码仍可能通过已有测试，单个示例仍可能正常运行，但系统已经失去一份能够定义整体处理范围的契约。

## 我们发现的核心问题

### Schema 不可见，也不一定可信

SQL 数据库通常有显式 DDL，但应用真正遵守的契约还可能散落在 ORM、接口类型和业务代码里。许多 NoSQL 或文档型系统允许更自由的数据形状，实际 Schema 往往只隐藏在读写代码中，甚至根本没有一份可独立取得的定义。

因此，Agent 面对一份数据时，第一个问题经常不是“如何使用”，而是“应该去哪里找到它的 Schema”。即使找到了某个类型或校验器，也很难立刻判断它是否就是当前数据的权威契约。

### 隐式 Schema 让程序的处理边界变得暧昧

当 Schema 只存在于处理代码中，程序的 scope——它明确支持、明确拒绝和行为未定义的数据范围——就无法被直接观察。这会产生两类实际风险。

第一，面对一个新输入，开发者和 Agent 都无法预先判断程序能否正确处理它。尝试支持这个输入之前，很难评估需要修改多少代码；修改之后，也很难系统判断哪些历史输入不再兼容。测试样例只能说明已覆盖的点，不能证明点与点之间或边界之外的行为。

第二，模块之间不再拥有可验证的组合契约。假设上游模块 A 产生一组输出，下游模块 B 的处理逻辑可能只覆盖其中一部分。A 的输出类型与 B 的输入能力看似相近，实际交集却不明确。落在交集之外的数据可能被静默丢弃、错误解释、部分处理或触发偶发异常，结果取决于代码路径而不是一份预先可检查的契约。

因此，问题不只是“缺少文档”。缺少显式 Schema 意味着无法计算兼容范围，无法可靠评估变更影响，也无法在模块连接之前证明生产者的全部输出都能被消费者接受。

### Schema 与数据会随时间漂移

当 Schema 与数据分开保存、独立发布时，两者会形成不同的生命周期。代码可能已经升级，持久化数据仍停留在旧形态；某个服务可能使用新类型，另一个服务仍按旧契约写入；文档也可能没有随实现更新。

这类漂移最危险的地方，是错误不一定立即发生。数据可能先被接受，直到另一个消费者读取时才暴露问题。此时很难回答：这份数据究竟违反了哪一个版本的契约？

### 结构正确不等于语义明确

`string`、`number`、数组和对象只能说明数据“长什么样”，不能说明它“代表什么”。例如，一个数字可能是毫秒、人民币分值、递增版本号或允许回退的状态值；一个字符串可能是展示名称、稳定标识符或外部系统引用。

缺少语义时，人类会依赖领域知识补全含义，Agent 则只能从字段名和调用代码中猜测。即使数据通过结构校验，也可能在业务语义上被错误使用。

### 编译期与运行期容易形成两套契约

为了改善开发体验，团队往往为同一数据手写 TypeScript 类型；为了保护运行期，又另外维护校验器或数据库约束。只要这些定义分别维护，它们就会逐渐分叉：编译器认可的写法可能被运行期拒绝，运行期允许的数据也可能无法被代码类型准确表达。

问题不在于检查太多，而在于检查所依据的真相不唯一。

### 协作与演进缺少可追溯上下文

当人类和多个 Agent 同时修改数据或围绕数据生成代码时，仅保存最终状态并不够。系统还需要处理并发编辑、记录变化，并让参与者明确自己所面对的数据契约。

传统的“数据在数据库、Schema 在代码仓库、说明在文档、历史在另一套日志”的布局，把一次变化拆散到了多个系统。重建某一时刻的上下文因而变得困难，也使重放、审计和故障分析成本上升。

## nomicore 的解决思路

### 让 Schema 成为数据，并与数据同行

nomicore 把一个命名空间定义为一个自包含的 Y.Doc：业务数据位于固定的 `ROOT`，Schema 以 `{ lang, version, id, text }` 信封存放在同一文档的 `SCHEMA` 中。Schema 不再只是部署在某处的代码，而是命名空间自身携带的数据。

由此建立的关键关系不是“一个中心 Schema 对应许多未知版本的数据”，而是每个命名空间都能回答：解释我，应当使用哪一种方言和哪一份 Schema 文本。

这并不意味着业务数据要复制 Schema 身份字段。`ROOT` 只承载业务数据；技术身份由同文档中的 `SCHEMA` 表达。两者同行，但职责分离。

### 用 VFSL 同时表达结构、载体和语义

nomicore 使用 VFSL（受限 TypeScript 子集、标记类型与 JSDoc）描述 Schema。这是当前已经落地的核心引擎能力。选择受限语言而不是任意 TypeScript，是为了让 Schema 可以被确定地解析、校验、哈希和跨版本解释；保留熟悉的 TypeScript 形态，则降低人类和代码生成 Agent 的理解成本。

VFSL 同时承载三类信息：

- **值结构**：字段、可选性、联合、动态键和 pattern 等约束；
- **Yjs 载体**：哪些节点物化为 `Y.Map`、`Y.Array`、`Y.XmlFragment` 或普通值；
- **业务语义**：通过 JSDoc 描述字段含义、单位、示例、角色和演进信息。

JSDoc 不只是仓库中的旁注文案。它进入 VFSL 的规范 IR，参与语义指纹，并随 `SCHEMA` 与数据一起传播。这样，Agent 获得的不仅是一棵可校验的结构树，还有理解和生成代码所需的领域提示。

### 从同一份 Schema 派生运行期与编译期能力

同一段 VFSL 文本可以派生结构树、值 Schema、路径索引和逻辑快照校验器，供运行期验证使用。编译期类型投影也从同一来源生成，为业务代码提供静态护栏。

两层检查各自承担不同职责：

- 编译期检查尽早阻止明显错误，让“坏代码更难写出来”；
- 运行期检查守住真实数据边界，让“坏数据进不来”。

编译期投影是派生物，不是第二份权威。目标态下，权威 VFSL 始终来自命名空间的 `SCHEMA`；仓库中的 Schema 文件只允许作为体系建设阶段的开发脚手架，并通过 `SchemaSource` 接缝隔离。

### 把失败变成 Agent 可处理的结构化反馈

对 Agent 友好不仅意味着语法熟悉，也意味着失败必须可定位、可解释、可用于下一轮修正。

nomicore 将预期失败建模为结构化结果，而不是依赖模糊异常。VFSL 解析错误包含稳定错误码和行列位置；数据校验问题指向具体路径；写入失败应说明哪份数据违反了哪一层契约。所有验证在事务写入之前完成，失败保持零写入，避免“报错了，但文档已经改了一半”。

显式 Schema 也把“是否支持这个输入”从一次探索性执行，转化为可以在边界处直接校验的问题。模块 A 的输出和模块 B 的输入不应再靠样例相似性推断兼容，而应分别由明确契约约束；不兼容数据在进入 B 之前就应被定位和拒绝。对于 Schema 演进，旧数据能否继续满足新契约也可以被系统检查，而不是等待某条代码路径偶然触发。

这形成了适合 Agent 的闭环：生成候选变更，提交校验，读取精确反馈，再据此修正，而不是从堆栈或后续故障中猜测原因。

### 用 Yjs 支撑人类与多个 Agent 协作

命名空间以 Y.Doc 为载体，使数据具备多人和多 Agent 协作所需的合并基础。让人类与 Agent 围绕同一命名空间实时协作是目标愿景；完整的网络同步、presence 与授权并不是当前已经交付的能力。

协作能力并不等于放弃约束。已经接受的运行时设计在 Yjs 之上建立受控写入管线：逻辑值先按 VFSL 验证，Yjs 实际载体再按派生结构检查，最终通过单次事务提交。同一命名空间的受控写入由单一 write sequencer 严格排序，使 Schema 切换、数据验证、事务提交和持久化标脏不会互相穿插。

### 让历史与数据使用同一条持久化路径

Schema 存放在 Y.Doc 中，因此 Schema 变化与业务数据变化都进入同一条 Yjs update 持久化路径。历史不再只是“代码仓库里曾经有过哪个类型”，而是能够覆盖命名空间实际发生的 Schema 与数据变更。

这种同源历史为审计和重放提供了基础：在设计可重放操作时，可以围绕同一份文档状态和同一套契约恢复上下文，而不必先拼接数据库快照、代码版本和外部 Schema 注册表。

nomicore 当前把持久化、缓存、flush 和 retry 与 VFSL 解释职责分层；更高层的操作日志、业务审计和完整重放协议仍需在相应边界上继续设计。

### 冻结方言，而不是冻结业务 Schema

Schema 可以演进，不代表解释规则可以悄然改变。nomicore 用 `lang + version` 标识 VFSL 方言：已经发布的方言冻结，只做兼容性加法；未知方言响亮失败，而不是猜测或降级解释。

这把两个常被混淆的版本分开：

- **业务 Schema 版本**可以随命名空间持续变化；
- **Schema 解释器版本**通过方言明确隔离，并保持历史语义稳定。

因此，系统既允许业务契约快速演进，又能避免同一段历史 Schema 文本在未来被解释成不同含义。

## DeepSeek Harness 带来的 Agent 范式升级

nomicore 的方向不只受到某个功能启发，更受到 DeepSeek Harness（DSH）所代表的 Agent 开发范式变化影响。回看 Agent 应用的发展，可以看到三个逐步放开控制权的阶段。

### 第一阶段：Workflow 中的有限智能

以 LangChain、Dify 为代表的早期框架主要由人类预先编写完整 Workflow：确定步骤、连线、分支和工具，再让模型在少数节点中理解文本、选择参数或生成内容。

这种方式可控，但弹性有限。系统真正会做什么，主要取决于人类事先画出的流程；AI 更像嵌入 Workflow 的智能组件，而不是能够自主组织工作、补齐能力的执行者。

### 第二阶段：以 Skill 为核心的开放执行

2026 年初，随着模型推理、工具使用和 coding 能力明显增强，Agent 开始转向以 Skill 为核心的架构。Skill 不再规定一条完整的固定流程，而是向模型提供领域知识、操作方法和完成标准，由模型根据任务动态组合步骤与工具。

这次变化大幅提高了灵活性，也降低了 Agent 开发门槛。不会编程的普通人也可以通过编写说明、沉淀经验和组合已有工具，搭建出非常实用的 Agent。

### 第三阶段：Agent 动态构造 Plugin

随着 Agent 的 coding 能力继续增强，DSH 的发布成为第三阶段的标志性事件：Agent 完成工作的核心不再只有预先提供的 Skill，还包括 Plugin；更关键的是，Plugin 可以由 Agent 根据当前任务动态编码、加载和使用。

这意味着 Agent 不只是调用人类准备好的能力，还可以发现能力缺口，为当前问题构造新的接口和执行逻辑，再把它集成回运行环境。Agent 开发由“人类预先穷举流程”进一步走向“人类给出目标和边界，Agent在运行中组织甚至扩展能力”。

### CLI 工具范式为何开始遇到瓶颈

现有 Agent 的大多数工具本质上是 Bash 工具或 CLI。CLI 很适合连接既有软件，但当 Agent 需要长时间、自主地推进复杂任务时，它暴露出一个共同问题：**工具在会话内，状态在会话外**。

具体表现为：

1. **状态位置和读取方式不统一。** 每个 CLI 都会改变某些数据，但数据存在哪里、采用什么结构、如何重新读取，通常由工具自己定义。Agent 只能分别学习文件、数据库、云服务或进程状态的访问方式。
2. **工具集合在会话开始时趋于固定。** 几千个工具不可能全部暴露给模型；把能力压缩进参数复杂的“大 CLI”，又会迫使 Agent 反复试探。另一种做法是在 Skill 中逐个写明工具路径和用法，但这会把运行时能力重新固化为人工维护的清单。
3. **外部状态变化对会话不可见。** 如果数据被人类、其他 Agent 或外部系统修改，当前会话通常不会自动知道，只能在下一次主动查询时偶然发现。
4. **进程恢复缺少确定锚点。** 执行中发生错误或进程重启时，如果没有 checkpoint，Agent 很难知道已经可靠完成了什么、应该从哪里继续，往往只能重新读取大量外部状态，甚至从头执行。

工具越多、任务越长、参与者越多，这些问题就越明显。它们不是简单增加几个 CLI 参数可以解决的，因为根因在于状态、事件、工具暴露和会话生命周期彼此分离。

### DSH 把状态重新带回 Agent 系统

DSH 的新范式把关系反转过来：数据由 DSH 管理，Tool 是访问和改变这些数据的受控接口，而不是各自携带一套不可见状态的外部命令。

由此可以建立四项关键能力：

1. **状态内聚。** Agent 操作的数据在 DSH 内部拥有明确位置和访问接口，Tool 围绕数据能力组织。
2. **持久化与 checkpoint。** 状态可以持久化，并回到上一个确定节点；任务恢复不必依赖模型重新猜测执行现场。
3. **变化可事件化。** 数据更新经过 DSH，系统可以自然地产生 event，主动让 LLM 会话获知人类、其他 Agent 或 Plugin 带来的变化。
4. **按状态暴露能力。** 每一轮可以根据 DSH 内部数据和任务阶段，决定向模型暴露哪些 Tool，也就是当前允许哪些数据操作。模型不必一次背负整个工具宇宙，权限和能力也可以随状态变化。

在这个模型中，Skill 仍然负责告诉 Agent 如何思考和完成一类任务，Plugin 负责提供可执行能力，而持久化状态、事件和动态 Tool 面共同构成 Agent 可以持续工作的环境。

### 这对 nomicore 意味着什么

DSH 解决了 Agent 运行环境如何管理状态、事件和动态能力的问题，也进一步暴露了数据层必须回答的问题：这些内部数据采用什么结构？每个 Plugin 可以安全读取和写入什么？状态演进后，旧 Plugin 是否仍然兼容？动态生成的 Plugin 如何获得准确的数据语义和可操作的校验反馈？

这正是 nomicore 希望补上的基础。Schema 与数据同行，让动态生成的 Plugin 不必从散落代码中猜测状态形状；同一份 Schema 派生运行期校验和编译期类型，使 Agent 写出的 Plugin 能在集成前后接受一致约束；结构化错误给 Agent 提供修正闭环；同源历史则为 checkpoint、恢复和重放保留解释状态所需的契约上下文。

可重放性在这里不仅是保存一次工具调用。Agent 行为、Plugin 代码、数据写入以及写入时生效的 Schema 都可能影响结果。nomicore 还没有把完整的 Agent 请求重放定义为已完成能力，但它把数据层建设在有利于恢复这些上下文的基础之上。

## 有意划定的边界

最初的思考包含“authority rules”：例如版本号只能递增、状态只能按状态机迁移。这类约束描述的是跨状态的业务不变量，而不仅是当前快照的结构和值域。

nomicore 当前有意把旧系统的 authority 规则体系排除在范围外，不保留兼容接口。现阶段的核心写入管线收敛为：结构检查、值校验和单事务提交。这样可以先把 Schema 单一真相、自包含命名空间、运行期验证和协作载体做深，而不是同时复制旧系统的所有职责。

这一区分很重要：

- VFSL 回答“当前这份值是否符合当前 Schema”；
- 跨版本单调性、状态迁移、授权与其他动态规则属于更高层能力，需要单独设计其模型、错误域与执行边界。

类似地，nomicore 是对 yjs-server 的完整重写，不是对旧系统的局部修补。旧服务端中的鉴权、presence、网络协议兼容和其他职责不会因为数据模型已经确定就自动获得解决，它们需要在后续阶段被显式设计。

## 我们希望得到什么

nomicore 最终希望建立的，不只是一种 Schema 语言或一个 Yjs 服务端，而是一套适合人类与 Agent 共同工作的可靠数据基础：

- 任意命名空间都自带可解释的当前契约；
- Schema、语义和数据同行，减少寻找与漂移；
- 运行期校验和编译期类型来自同一真相源；
- 错误能够精确指出位置、路径和违反的契约；
- 校验失败保持零写入，成功写入具有明确顺序和原子边界；
- 人类与多个 Agent 最终可以围绕同一份协作数据工作；
- Schema 和数据的变化进入同源历史，为审计与重放奠定基础；
- 业务 Schema 可以高速演进，而历史解释规则保持稳定。

当代码生产速度不再是主要限制，系统能否提供清晰、可信、可演进的数据契约，就会成为新的基础能力。nomicore 正是从这个判断出发。
