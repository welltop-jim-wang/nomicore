# 为什么启动 nomicore

本文说明 nomicore 的出发点：在 Agent 参与软件开发成为常态后，我们需要怎样的数据基础设施；现有方案暴露了哪些问题；nomicore 又选择了怎样的解决路径。

这不是接口规格或当前版本功能清单。文中会明确区分**已经实现的能力**、**ADR 已接受但仍在建设的目标**与**长期愿景**。具体术语与架构决策以 [`CONTEXT.md`](../CONTEXT.md) 和 [`docs/adr/`](adr/) 为准，当前可运行能力以 [`README.md`](../README.md) 为准。

## 从一个朴素事实出发：代码总是在消费和产生数据

无论软件表面上提供的是页面、接口、工作流还是智能体，它的核心活动都离不开两件事：读取数据，并产生新的数据。

传统开发中，人类通常同时掌握代码、数据库、接口约定和业务背景。即使契约分散在 SQL DDL、ORM model、TypeScript 类型、校验器和文档里，人也常能凭经验把它们拼起来。这个过程代价不低，但迭代速度有限时，问题尚可被人工协调掩盖。

Agent 改变了这个前提。Agent 可以快速生成、修改并集成代码，却不会天然拥有团队成员脑中的隐含上下文。它需要从系统中直接获得三个答案：

1. 这份数据的结构是什么？
2. 这份数据在业务上是什么意思？
3. 一次写入怎样才算有效？

如果答案只能通过搜索代码、猜测命名、追查迁移记录和询问人类才能拼出，那么代码生成越快，错误契约被放大的速度也越快。对 Agent 友好的开发环境，首先需要一个对 Agent 友好的数据层。

## Agent 加速开发后，数据层成为新的瓶颈

Agent 驱动的高频迭代要求 Schema 可以持续演进，而不是在 day one 被假定为已经设计完毕。与此同时，快速变化不能以弱化契约为代价：整个数据面仍应接受强 Schema 校验，否则每一次局部改动都可能制造新的数据形态，最终产生难以识别的 Schema drift。

这里存在一个表面矛盾：

- Schema 必须足够稳定，才能可靠地约束读写；
- Schema 又必须能够演进，才能跟上业务和 Agent 的迭代速度。

nomicore 的出发点不是在“固定 Schema”和“无 Schema”之间二选一，而是让每一个时刻都存在明确、可验证的当前契约，同时让契约本身也成为可以被管理、持久化和演进的数据。

## 我们发现的核心问题

### Schema 不可见，也不一定可信

SQL 数据库通常有显式 DDL，但应用真正遵守的契约还可能散落在 ORM、接口类型和业务代码里。许多 NoSQL 或文档型系统允许更自由的数据形状，实际 Schema 往往只隐藏在读写代码中，甚至根本没有一份可独立取得的定义。

因此，Agent 面对一份数据时，第一个问题经常不是“如何使用”，而是“应该去哪里找到它的 Schema”。即使找到了某个类型或校验器，也很难立刻判断它是否就是当前数据的权威契约。

### Schema 与数据会随时间漂移

当 Schema 与数据分开保存、独立发布时，两者会形成不同的生命周期。代码可能已经升级，持久化数据仍停留在旧形态；某个服务可能使用新类型，另一个服务仍按旧契约写入；文档也可能没有随实现更新。

这类漂移最危险的地方，是错误不一定立即发生。数据可能先被接受，直到另一个消费者读取时才暴露问题。此时很难回答：这份数据究竟违反了哪一个版本的契约？

### 结构正确不等于语义明确

`string`、`number`、数组和对象只能说明数据“长什么样”，不能说明它“代表什么”。例如，一个数字可能是毫秒、人民币分值、递增版本号或允许回退的状态值；一个字符串可能是展示名称、稳定标识符或外部系统引用。

缺少语义时，人类会依赖领域知识补全含义，Agent 则只能从字段名和调用代码中猜测。即使数据通过结构校验，也可能在业务语义上被错误使用。

### 编译期与运行期容易形成两套契约

为了改善开发体验，团队往往为同一数据手写 TypeScript 类型；为了保护运行期，又另外维护校验器或数据库约束。只要这些定义分别维护，它们就会逐渐分叉：编译器认可的写法可能被运行期拒绝，运行期允许的数据也可能无法被代码类型准确表达。

问题不在于检查太多，而在于检查所依据的真相不唯一。

### 协作与演进缺少可追溯上下文

当人类和多个 Agent 同时修改数据或围绕数据生成代码时，仅保存最终状态并不够。系统还需要处理并发编辑、记录变化，并让参与者明确自己所面对的数据契约。

传统的“数据在数据库、Schema 在代码仓库、说明在文档、历史在另一套日志”的布局，把一次变化拆散到了多个系统。重建某一时刻的上下文因而变得困难，也使重放、审计和故障分析成本上升。

## nomicore 的解决思路

### 让 Schema 成为数据，并与数据同行

nomicore 把一个命名空间定义为一个自包含的 Y.Doc：业务数据位于固定的 `ROOT`，Schema 以 `{ lang, version, id, text }` 信封存放在同一文档的 `SCHEMA` 中。Schema 不再只是部署在某处的代码，而是命名空间自身携带的数据。

由此建立的关键关系不是“一个中心 Schema 对应许多未知版本的数据”，而是每个命名空间都能回答：解释我，应当使用哪一种方言和哪一份 Schema 文本。

这并不意味着业务数据要复制 Schema 身份字段。`ROOT` 只承载业务数据；技术身份由同文档中的 `SCHEMA` 表达。两者同行，但职责分离。

### 用 VFSL 同时表达结构、载体和语义

nomicore 使用 VFSL（受限 TypeScript 子集、标记类型与 JSDoc）描述 Schema。这是当前已经落地的核心引擎能力。选择受限语言而不是任意 TypeScript，是为了让 Schema 可以被确定地解析、校验、哈希和跨版本解释；保留熟悉的 TypeScript 形态，则降低人类和代码生成 Agent 的理解成本。

VFSL 同时承载三类信息：

- **值结构**：字段、可选性、联合、动态键和 pattern 等约束；
- **Yjs 载体**：哪些节点物化为 `Y.Map`、`Y.Array`、`Y.XmlFragment` 或普通值；
- **业务语义**：通过 JSDoc 描述字段含义、单位、示例、角色和演进信息。

JSDoc 不只是仓库中的旁注文案。它进入 VFSL 的规范 IR，参与语义指纹，并随 `SCHEMA` 与数据一起传播。这样，Agent 获得的不仅是一棵可校验的结构树，还有理解和生成代码所需的领域提示。

### 从同一份 Schema 派生运行期与编译期能力

同一段 VFSL 文本可以派生结构树、值 Schema、路径索引和逻辑快照校验器，供运行期验证使用。编译期类型投影也从同一来源生成，为业务代码提供静态护栏。

两层检查各自承担不同职责：

- 编译期检查尽早阻止明显错误，让“坏代码更难写出来”；
- 运行期检查守住真实数据边界，让“坏数据进不来”。

编译期投影是派生物，不是第二份权威。目标态下，权威 VFSL 始终来自命名空间的 `SCHEMA`；仓库中的 Schema 文件只允许作为体系建设阶段的开发脚手架，并通过 `SchemaSource` 接缝隔离。

### 把失败变成 Agent 可处理的结构化反馈

对 Agent 友好不仅意味着语法熟悉，也意味着失败必须可定位、可解释、可用于下一轮修正。

nomicore 将预期失败建模为结构化结果，而不是依赖模糊异常。VFSL 解析错误包含稳定错误码和行列位置；数据校验问题指向具体路径；写入失败应说明哪份数据违反了哪一层契约。所有验证在事务写入之前完成，失败保持零写入，避免“报错了，但文档已经改了一半”。

这形成了适合 Agent 的闭环：生成候选变更，提交校验，读取精确反馈，再据此修正，而不是从堆栈或后续故障中猜测原因。

### 用 Yjs 支撑人类与多个 Agent 协作

命名空间以 Y.Doc 为载体，使数据具备多人和多 Agent 协作所需的合并基础。让人类与 Agent 围绕同一命名空间实时协作是目标愿景；完整的网络同步、presence 与授权并不是当前已经交付的能力。

协作能力并不等于放弃约束。已经接受的运行时设计在 Yjs 之上建立受控写入管线：逻辑值先按 VFSL 验证，Yjs 实际载体再按派生结构检查，最终通过单次事务提交。同一命名空间的受控写入由单一 write sequencer 严格排序，使 Schema 切换、数据验证、事务提交和持久化标脏不会互相穿插。

### 让历史与数据使用同一条持久化路径

Schema 存放在 Y.Doc 中，因此 Schema 变化与业务数据变化都进入同一条 Yjs update 持久化路径。历史不再只是“代码仓库里曾经有过哪个类型”，而是能够覆盖命名空间实际发生的 Schema 与数据变更。

这种同源历史为审计和重放提供了基础：在设计可重放操作时，可以围绕同一份文档状态和同一套契约恢复上下文，而不必先拼接数据库快照、代码版本和外部 Schema 注册表。

nomicore 当前把持久化、缓存、flush 和 retry 与 VFSL 解释职责分层；更高层的操作日志、业务审计和完整重放协议仍需在相应边界上继续设计。

### 冻结方言，而不是冻结业务 Schema

Schema 可以演进，不代表解释规则可以悄然改变。nomicore 用 `lang + version` 标识 VFSL 方言：已经发布的方言冻结，只做兼容性加法；未知方言响亮失败，而不是猜测或降级解释。

这把两个常被混淆的版本分开：

- **业务 Schema 版本**可以随命名空间持续变化；
- **Schema 解释器版本**通过方言明确隔离，并保持历史语义稳定。

因此，系统既允许业务契约快速演进，又能避免同一段历史 Schema 文本在未来被解释成不同含义。

## 来自 DeepSeek Harness 的启发

nomicore 的方向也受到 DeepSeek Harness 实践的启发。

第一，Agent 的价值不只在于生成建议，而在于能够在运行中产出正确代码、验证代码，并把结果集成回真实系统。要支持这条链路，系统必须给 Agent 清晰的契约、可靠的工具和可操作的错误反馈。

第二，动态 Schema 不应只服务运行期。若同一份 Schema 还能投影为代码类型，那么增加编译期检查的成本很低，却能把大量错误提前到生成和集成阶段。关键仍然是所有检查从同一个权威源派生，而不是新增一份需要手工同步的定义。

第三，可重放性很重要。Agent 行为、工具调用和数据写入都可能需要复现。把 Schema、数据及其变更历史放在可追踪的同一载体中，可以减少重放时缺失上下文的风险。nomicore 还没有把完整的 Agent 请求重放定义为已完成能力，但它把数据层建设在有利于重放的基础之上。

## 有意划定的边界

最初的思考包含“authority rules”：例如版本号只能递增、状态只能按状态机迁移。这类约束描述的是跨状态的业务不变量，而不仅是当前快照的结构和值域。

nomicore 当前有意把旧系统的 authority 规则体系排除在范围外，不保留兼容接口。现阶段的核心写入管线收敛为：结构检查、值校验和单事务提交。这样可以先把 Schema 单一真相、自包含命名空间、运行期验证和协作载体做深，而不是同时复制旧系统的所有职责。

这一区分很重要：

- VFSL 回答“当前这份值是否符合当前 Schema”；
- 跨版本单调性、状态迁移、授权与其他动态规则属于更高层能力，需要单独设计其模型、错误域与执行边界。

类似地，nomicore 是对 yjs-server 的完整重写，不是对旧系统的局部修补。旧服务端中的鉴权、presence、网络协议兼容和其他职责不会因为数据模型已经确定就自动获得解决，它们需要在后续阶段被显式设计。

## 我们希望得到什么

nomicore 最终希望建立的，不只是一种 Schema 语言或一个 Yjs 服务端，而是一套适合人类与 Agent 共同工作的可靠数据基础：

- 任意命名空间都自带可解释的当前契约；
- Schema、语义和数据同行，减少寻找与漂移；
- 运行期校验和编译期类型来自同一真相源；
- 错误能够精确指出位置、路径和违反的契约；
- 校验失败保持零写入，成功写入具有明确顺序和原子边界；
- 人类与多个 Agent 最终可以围绕同一份协作数据工作；
- Schema 和数据的变化进入同源历史，为审计与重放奠定基础；
- 业务 Schema 可以高速演进，而历史解释规则保持稳定。

当代码生产速度不再是主要限制，系统能否提供清晰、可信、可演进的数据契约，就会成为新的基础能力。nomicore 正是从这个判断出发。
