# ADR 0026：原子变更信封——批量多操作全有或全无

日期：2026-09-12
状态：已接受

## 背景与动机

一次业务命令往往要写多个值（状态转移同时改 status、reviewedAt、reviewer；创建条目同时写多个字段）。现状下 mutateData 信封只承载单个操作，多值命令只能拆成 N 次独立的受控写：每次各占一个写槽，中间态对并发读者可见（status 已变、reviewedAt 未设），任一步失败留下部分提交的残缺状态。typed-access 技能文档曾以「多节点命令显式定义部分失败/原子性语义」作为妥协立场——把原子性推给上层。

本 ADR 把多操作原子性收进引擎：mutateData 的一次变更尝试可携带多个操作，**全有或全无**（all-or-nothing）——任一操作预检失败则整体零写入，全部成功则单事务按序提交。批量是独立正当的基础能力，不依附于任何前置条件场景（条件写 guard 由 ADR 0025 后续叠加，见「与 ADR 0025 的组合」）。

## 决策

### 信封形态（双形态并存，互斥）

```ts
// 形态一：单操作对象——现役契约，逐字节不变
{ op: 'set', path: [...], value: x }

// 形态二：批量信封（本 ADR 新增）
{ ops: [
  { op: 'set', path: ['tasks', id, 'status'], value: 'reviewing' },
  { op: 'set', path: ['tasks', id, 'reviewedAt'], value: ts },
  { op: 'set', path: ['tasks', id, 'reviewer'], value: uid },
] }
```

- 信封是普通对象，**恰提供两种形态之一**：单操作字段组（`op`/`path`/…）或 `ops` 数组；同现 = 形状错误。
- `ops` 约束：非空数组、数量上限 **16**、每个元素是完整合法的单操作信封、**元素不得携带 `guard` 键**（guard 属 ADR 0025 的批级前提，届时只允许出现在顶层）。
- **批内路径互不嵌套**：任意两个操作的路径不得构成祖先-后代或相同关系——嵌套批量存在「父替换与子写顺序」歧义，v1 在信封解析期直接拒绝为形状错误。

### 槽内次序与原子性

- 次序：**逐操作 prepare**（解析/导航/detached 构建/校验）→ 任一失败**整体零写入** → 全部成功**单事务按序提交** → 逐操作边界验证。
- 原子性归属与 ADR 0025 同构：**写序列器 FIFO 独占 + 单 Yjs 事务**。观察者要么看到全部操作生效、要么都不见；跨实体路径同样原子（Yjs 事务覆盖整个 doc）。
- 各操作仍是最小 edit（`set` 叶子 / `array-insert` 局部等）——**原子性不以载体降级换取**：不整父替换、不重建容器，Yjs 同步粒度与并发合并面完整保留。这是批量信封相对「整父替换 + 乐观锁」形态的本质优势。

### 错误域

- **形状错误**（双形态同现、`ops` 非法、元素非单操作信封、元素携带未知键、路径嵌套、超上限）→ 信封校验拒绝，无码，不可重试。
- **操作失败**（某个操作的导航/校验/构建失败）→ 零写入 `ok:false`，**聚合全部**失败操作的 issues（批量是调用方一次构造的静态集合，全量反馈减少修正轮次；与 schema 校验 issues 多条先例一致）——不是 fail-fast 单错。
- fatal 通道不变；本 ADR 无新增稳定码。

### 诊断

一个写槽 = 一次变更尝试 = 一条诊断记录；单事务天然产出**单条 update bytes**——多值命令在重放面上是一条原子增量，而非 N 条松散尝试。

### 边界与不承诺

- 只覆盖单实例受控写：复制 apply（replication-unvalidated）与 `replaceSchema` 不适用。
- 跨实例语义不变：各操作仍按 Yjs 元素语义合并，批量不改变 CRDT 收敛行为。

### 与 ADR 0025 的组合

ADR 0025（已接受、未实现）的条件写 guard 键后续叠加于**两种形态的顶层**：单操作对象可带 `guard`，`{ ops, guard }` 批量顶层亦可带 `guard`；guard 评估先于逐操作 prepare（0025 已定的「guard 先于一切」次序在批量下不变）。批内元素永远不得携带 guard——guard 是整批前提，需要逐操作条件时应拆为多次变更尝试。**实现顺序：本 ADR 先行，0025 随后**——guard 落地时直接同时支持两种形态，避免先单形态再扩展的二次返工。

## Considered Options

- **重构并入 ADR 0025**：把 0025 改写为「原子变更信封（批量 + 条件）」整体叙事——被否：0025 已按条件写窄叙事成文并派生 spec 与票面；批量独立正当、独立成文，且先行实现为 guard 提供完整落点。
- **整父替换 + guard equals 整父旧值（乐观锁）**：能表达原子多字段但以载体降级换原子（重建容器、丢弃同步粒度）——被否。
- **上层顺序写 + 显式部分失败补偿**（现状）：中间态可见、残缺状态残留、诊断面松散——被否（见背景）。

## Consequences

- mutateData 信封演进为双形态；单操作形态逐字节不变，旧调用方零影响；携带 `ops` 的信封对旧运行区按未知信封键 loud 拒绝。
- typed-access 技能文档改写「多节点命令」立场：多值业务命令**优先使用批量信封**，不再要求上层显式定义部分失败语义。
- CONTEXT.md 新增「原子变更（atomic mutation）」词条，修订「条件写」词条为两种形态顶层皆可携带。
- ADR 0025 增补「与 ADR 0026 的组合」节；实现票序：本 ADR 批量票先行，#347–#349（guard）排其后。
- 实现验证门槛：doc-runtime 批量解析/prepare/单事务提交测试、namespace-runtime mutateData 批量端到端与诊断单条记录测试、根 `pnpm typecheck` + `pnpm test`。

## 开放问题

1. `ops` 上限 16 的词表演进（放宽须过设计评审）。
2. 批内嵌套的受控放宽（若未来需要「父替换 + 子写」顺序语义，须先定义顺序规则，独立决策）。
3. 单操作形态是否长期保留为 `ops` 长度 1 的语法糖（文档措辞演进，非契约变更）。
