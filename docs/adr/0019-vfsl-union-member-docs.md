# ADR 0019：VFSL 联合成员文档注释（M4 挂载锚位）

日期：2026-09-11
状态：已接受
跟踪：issue #304

## 背景与动机

从语义和口径的角度，联合（枚举）成员是需要逐成员描述的重要声明性节点：枚举的
每个字面量、判别联合的每个变体都有自己的领域含义（状态机迁移语义、变体的载体
选择理由、废弃变体的兼容说明）。schema-authoring-guide §8 已要求「枚举与联合：
每个字面量或变体代表的领域状态」用文档注释承载，但 v1 的文档注释只有三个挂载
锚位（M1 类型别名 / M2 对象字段 / M3 标记类型，v1-spec §5）——写在联合成员前
的 `/** */` 没有任何锚位回收，parser 集中式记账将其留在悬空候选，模块末以
VFSL-E305 拒绝。

结果是逐成员语义无处安放，只能挤在外层别名或字段的一条 doc 里：

```vfsl
/** 订单生命周期状态：draft=可编辑；submitted=已提交只可追加备注；archived=终态只读 */
type Status = "draft" | "submitted" | "archived";
```

成员与口径的对应关系靠读者自行对齐，AI 消费方、生成文档与 codegen 生成物都拿
不到结构化的逐成员语义。

本 ADR 新增第四类挂载锚位 **M4（联合成员）**，是 v1 方言的「只增」演进：仅让
原本 E305 拒绝的文本变为合法，不改变任何既有合法文本的语义、物化、指纹或错误
码（合规论证见决策 9）。

## 决策

### 1. M4 锚位规则

联合成员的文档注释按以下规则挂载（锚位 = doc 经 tokenizer 侧通道挂靠的记号）：

- 成员有前导 `|` 时（含首成员的前导 `|`），锚位是该 `|` 记号——doc 紧邻 `|`
  之前，挂载到 `|` 之后的成员；
- 首成员无前导 `|` 时，锚位是成员起始记号——doc 紧邻成员起点之前，挂载到该
  成员；
- 连续多条 doc 按出现顺序全部挂载到同一成员（与 M1/M2/M3 的既有规则同构）；
- `|` 与成员之间的 doc（如 `| /** d */ "b"`）不属 M4 挂载范围：非标记成员 →
  维持 E305；成员起始记号为标记名时按 M3 挂标记节点（既有行为，见决策 3）。

规范写法（多行前导 `|` 布局，社区主流风格）：

```vfsl
/** 订单生命周期状态 */
type Status =
  /** 草稿：可继续编辑，未进入处理流 */
  | "draft"
  /** 已提交：进入处理流，只可追加备注 */
  | "submitted"
  /** 已归档：终态，只读 */
  | "archived";
```

单行与混合布局同样合法：`type T = /** 甲 */ "a" | "b";`（首成员锚位 = 成员
起始记号）、`"a" /** 乙 */ | "b"`（doc 紧邻 `|` 之前 → 挂 `"b"`——doc 是其
后继节点的 Leading 注释，与既有 M1/M2/M3 锚位的「紧随其后」语义一致）。

### 2. 单成员坍缩维持 E305

单成员联合按 §7.3 坍缩、不产联合节点，成员 doc 无挂载目标：`type T =
/** d */ "a";` 与 `type T = /** d */ | "a";` 维持 E305，与现行行为逐字节一致。
不升格挂别名节点——那会与 M1（`type` 前的别名 doc）抢同一槽位，两条 doc 语义
混淆。

### 3. M3 优先于 M4（不双挂）

成员起始记号为标记名时（如 `type T = /** d */ YLeaf<"a"> | YLeaf<"b">;`），doc
按既有 M3 挂标记节点，M4 不再回收——同一 doc 不双挂。这不是偏好选择而是冻结
约束：该文本在 v1 已是合法文本且 doc 挂 M3，改为 M4 优先 = 重新解释既有构造的
挂载语义，违反 v1-spec §8「语义不改」。推论：`/** 成员口径 */ | /** 载体口径 */
YLeaf<"a">` 这种夹缝叠写在标记成员上合法（两条 doc 各归各的锚位），在非标记成
员上第二条 E305——不对称是「语义不改」的代价，spec 修订中显式注明。

### 4. IR：`union.memberDocs` 条件附加

IR union 节点新增 `memberDocs?: string[][]`：与 `members` 等长对齐，无 doc 成员
为空数组；**全体成员均无 doc 时整键不存在**。条件附加是强制项而非风格选择：
semantic 指纹 = IR 紧凑 JSON 的 SHA-256（fingerprint.ts），空槽以必填键入场会
改写全部存量含联合文本的指纹输入 = 兼容性事故。仅使用 M4 的新文本携带此键，
存量文本的 IR 与指纹逐字节不变，故 `sha256:v1:` 域文档前缀不变（D2 升级触发器
不命中：v1 摘要可解释的文档语言未变，新键只出现在 v1 原本拒绝的文本上）。

parser 内部 AST 的 union 节点恒携带 `memberDocs`（必填、等长），AST → IR 转换
（semantic.ts）时按上述条件附加。M4 的 parser 回收采用「记录位置 + 终局核对」：
成员数需扫到表达式末尾才可知（坍缩判定），同步回收约束不成立；每成员记录其前
导 doc 在 dangling 中的区间与 DocLead 引用，确认 ≥2 成员后按成员逆序以引用同
一性核对回收（核对失败 = 已被 M3 等内部锚位回收）；坍缩时整条不回收，doc 留
在悬空候选 → E305。

### 5. derived：条件稀疏 `memberDocs` 表（修订 ADR 0003）

DerivedSchema 新增 `memberDocs?: Record<string, string[]>`：键 = 成员语法路径
（既有 `<member N>` 合成段，如 `Status.<member 1>`、`ROOT.assets.<key>.<member
0>`），值 = 成员 doc 逐字继承。**条件稀疏**：仅当模块至少一名成员携带 doc 时整
键在场，且表内只收非空条目——存量 schema 的派生物逐字节不变（不同于
fieldDocs/markerDocs 的全量立行惯例，差异常态化写在类型注释里）。手造 IR 的
loud 边界同族延伸：`memberDocs` 在场但非等长数组的数组 → TypeError → E100。

这是对 ADR 0003「派生 schema 冻结形状」docs 表条款的修订：docs 承载从三张表
扩为四张表，新增表条件附加。

### 6. codegen：四个发射位

生成物让成员语义随类型投影到达所有消费方（hover、AI 读码、生成文档）：

1. **别名判别联合**：成员 doc 以 `  | ` 行为基准上一行发射逐成员 TSDoc；
2. **别名枚举**（标量字面量联合在两树坍缩为 leaf/enum，成员边界仅从
   memberDocs 表按 `<member N>` 路径回填）：有成员 doc 时转多行布局——

   ```ts
   /** 订单生命周期状态 */
   export type Status =
     /** 草稿：可继续编辑，未进入处理流 */
     | 'draft'
     /** 已提交：进入处理流，只可追加备注 */
     | 'submitted'
     /** 已归档：终态，只读 */
     | 'archived';
   ```

   无成员 doc 时保持既有单行布局，存量生成物逐字节不变；
3. **内联联合**（字段类型位等）：成员 doc 行内前置（`/** d */ Member | …`）；
4. **内联枚举**：同行内前置。

YPlainArray 纯值子树与 YXmlFragment 不透明实参内的成员 doc 无发射位（丢弃），
与 fieldDocs/markerDocs 在这些位置的既有限界同族；derived 表照常收集。

### 7. readData 语义投影切片并入（修订 ADR 0016）

`resolveSchemaAtPath` 的 docs 切片并入 memberDocs 为第三来源：选键规则不变
（脊柱 ∪ 终点子树后代 ∪ 闭包别名内部——`<member N>` 路径天然落在既有规则内），
合并内容 `docs[k] = [...fieldDocs[k], ...markerDocs[k], ...memberDocs[k]]`
（member 末位；fieldDocs 在 `<member N>` 键上恒无条目，实际合并 = marker 在前
member 在后），空条目过滤不变。投影返回形状（valueSchema/aliases/docs/
aliasDocs 四件套）不变，namespace-runtime 的 detached 克隆零改动。这修订 ADR
0016 的 docs 切片条款（两来源 → 三来源），仅对使用 M4 的 schema 产生新切片内
容。

### 8. 纯文档性质不变

成员 doc 与既有三锚一致，是文档性质（ADR 0001「无机器标签」）：不进校验规则、
不进物化行为、不作机器语义的输入。校验错误信息回带成员 doc 明确不做——
validate.ts 目前不读任何 docs，该口子不由本特性打开。

### 9. 只增不改合规论证（v1-spec §8 逐条）

1. **语法只增**：M4 只让原本 E305 拒绝的文本（成员前 doc）变合法；未收窄或废
   除任何 v1 已有推导。保留名集合、词法、EBNF 产生式零改动；
2. **语义不改**：既有合法文本的物化、挂载、错误语义逐字节不变——无成员 doc
   的联合 IR 不携带新键（指纹稳定）、derived 不出现新表、生成物布局不变、E305
   的既有触发场景（含决策 2 的坍缩情形）全部保持；
3. **错误码稳定**：不新增错误码，E305 的条件是「减去 M4 新锚位」的缩小，既有
   触发条件与含义不变；E305 消息正文的可挂载节点枚举补「联合成员」（消息措辞
   不冻结，锚注释起始不变）。

### 10. 明确不做的部分与后续方向

- 不改变 tokenizer 侧通道（`|` 照常吸收 pending doc；M4 的锚位规则是对该机制
  的利用而非修改）；
- 不为单成员坍缩场景发明挂载目标（决策 2）；
- 不在校验错误中回带成员 doc（决策 8）；
- **后续方向指针**：数值范围约束（如正整数）已识别未实施——预研结论为
  `number & Int<min, max>` 镜像 `string & Pattern<"…">` 的交叉特例，闭区间整数
  界完备（整数域上 `>0` ≡ `≥1`，无需开区间记法）；新增保留名属「收窄」，实施
  前需 owner 裁决走 v1 修订例外（§8 首次发布前豁免）还是方言 v2（信封
  `version: 2`）。届时另立 ADR。

## Considered Options

- **锚位一律为成员起始记号（tokenizer 穿透 `|`）**：被否决。需改 tokenizer 侧
  通道让 `|` 不吸收 pending doc，影响全部既有 E305 判定面；方案 A 用两条锚位子
  规则在 parser 内达成同一作者意图，零词法改动。
- **仅前导 `|` 布局可挂成员 doc**：被否决。规则最简但 `type T = /** d */ "a" |
  "b"` 这种自然写法 E305，ergonomics 不可接受。
- **坍缩场景的 doc 升格挂别名**：被否决（决策 2，与 M1 抢槽位）。
- **derived memberDocs 全量立行（空数组条目）**：被否决。与三表惯例同构是优点，
  但所有含联合的存量 schema 派生物都会多出空条目键；条件稀疏保住逐字节稳定。
- **成员 doc 参与校验错误回带**：被否决（决策 8）。

## Consequences

- 实现改动面（挂本设计 PR 之下的实现 ticket）：
  - `packages/vfsl`：parser.ts（M4 延迟回收 + AST union.memberDocs）、ir.ts
    （条件键 + 指纹纪律注）、semantic.ts（条件附加转换 + E305 消息措辞）、
    derived.ts（条件稀疏表）、evaluate.ts（walkDocs 收集 + 手造 IR 守卫）、
    resolve-schema-at-path.ts（sliceDocs 第三来源）；
  - `packages/vfsl-codegen`：emitter.ts 四发射位（含枚举多行布局、
    semicolonFree 模式同布局）；
  - 文档：v1-spec §5 挂载规则修订（四类锚位 + M4 子规则 + 挂载示例）随实现
    PR 落地（避免「规格已改、实现未跟」的中间态）；schema-authoring-guide 第
    7/8 节与检查表同步；
- 测试矩阵：M4 两锚位子规则各正反例、连续 doc 累积、`|` 夹缝 doc 的 E305 与
  M3 优先、坍缩 E305 保持、IR 无 memberDocs 键（存量指纹稳定断言）、derived
  条件稀疏与 `<member N>` 键序、手造 IR 畸形守卫、codegen 四发射位文案与无
  doc 逐字节不变、投影切片并入、端到端（schema → derived → generated.ts）；
- 消费方影响：仅用 M4 的 schema 产生新可观测内容（IR 新键、derived 新表、
  生成物 doc 行、投影切片新条目）；一切存量 schema 的解析、派生、指纹、生成
  物与投影逐字节不变；
- 本 PR 转任本特性集成 PR：实现 ticket 挂其下、与设计同支累积，收官时人工合
  并（Ticket Parent 惯例）。
