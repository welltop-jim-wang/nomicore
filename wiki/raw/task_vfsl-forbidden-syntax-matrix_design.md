## §1. 需求推演（Feature）

### 1.1 交付物的本质

Issue #8 的验收标准（简报 §二 / TASK.md）逐条推演：

| AC | 要求 | 交付物形态 |
|---|---|---|
| AC-1 | 五类禁止语法各有负例：`ok: false` + 错误码前缀 + 锚点记号 line/column（按 v1-spec §4 锚点规定） | 测试体 |
| AC-2 | 每个负例配对「最接近的合法写法」正例通过（`ok: true`），证明拒绝精确而非一刀切 | 测试体 |
| AC-3 | 矩阵覆盖可在 vitest 报告中逐项指认（负例/正例成对、类别可辨识） | 测试文件的组织与命名 |

三条 AC 的交付物**全部是测试体**（Issue 原文：「覆盖矩阵以测试体呈现」）。生产代码（parser）在本任务中的角色是**被验证对象**，仅当矩阵暴露其判定漏洞时才成为修改对象（简报 §四.2）。这是本任务与 #5/#6/#7 的本质区别：**增量是验证资产，不是生产行为**。

### 1.2 需求边界（由 v1-spec frozen 条款锁定）

- 五类矩阵专属码：E101（`any`）/ E102（自定义泛型）/ E103（条件类型）/ E104（mapped type）/ E105（interface 声明族整族冻结）。**E106（递归/循环引用）明确排除**（简报 §一注；引用相位非语法相位）——SA6 矩阵无 E106 单元格，边界遵守正确。
- 锚点与优先级由 v1-spec §4「错误判定顺序」（规范性，7 条自上而下）+「一处构造命中多特征取文本位置最前」+ 分相位规则（语法相位即时失败；引用/语义相位仅当全量解析成功）唯一决定。矩阵期望值**必须从规范推导，不得从实现反推**。
- 公共接缝 `parseVfsl(text)` → `{ ok: true, module } | { ok: false, issues }` 冻结（PRD #3）；issues 形状 `{ message, line, column }`，错误码以 message 冻结前缀 `VFSL-E<编号>: ` 传递（v1-spec §4「错误码传递通道」）。
- **R1 修订补记**：AC-2 的字面要求约束的是 `-pos` 槽位的**断言形态**（`ok: true`），不只是槽位的存在——一个名为 `-pos` 实则断言失败的用例同时违反 AC-2 字面要求与测试文件自身头部契约（:13-17），并毒化 AC-3 的报告可指认性（vitest 报告中一行 `-pos` 实为负例，逐项指认时误导读者）。

## §3. 根因推演：矩阵为什么必然全绿（架构必然性）

Feature 任务的推演问题在这里变形为：**为什么一个为 #5 单点负例设计的判定顺序实现，能不经修改地覆盖 #8 的 38 单元格多维矩阵？** 答案在 #5 设计（`task_vfsl-parser-min-e2e_design.md`）的三项前瞻决策，它们使五类拒绝**按构造即「全位置泛化」**：

1. **Day 1 记号全集**（#5 设计 §记号表）：`interface` / `extends` / `any` / `<` / `[` 等锚点记号在 tokenizer 层 Day 1 齐备（`tokenizer.ts` 单字符标点全集含 `[ ] < >`；`interface`/`any`/`extends` 作为普通 ident 记号产出）。→ 矩阵的任何嵌套位置、任何 trivia 形态（空白/跨行）都能产出锚点记号，不存在「记号缺失导致 E104 在嵌套位降级为 E100」这类漏洞。

2. **判定顺序 1~7 逐条映射在递归下降的类型位置分派层**（`parseIdentType` / `parseObjectType` / `parseTypeAlias` / `parseModule`），而**类型位置是递归泛化的**：字段类型位、数组元素位、联合成员位、Record 键/值位、标记实参位全部经由同一 `parseTypeExpr → parseUnionType → parsePostfixType → parsePrimaryType → parseIdentType` 递归到达。→ 顶层写法与任意嵌套写法走**同一条代码路径**。#8 矩阵的「不同嵌套位置」维度不产生新路径，只重复验证同一路径。

3. **第 6 条延迟终判**（generic-diag 节点 + 语义相位裁定）：类型位置的 `Foo<Bar>` 调用形态在语法相位被平衡角括号扫描无损消费，终判推迟到语义相位按声明集合裁定（已声明→E100 锚 `<`；未声明→E301 锚引用记号），与「别名解析与声明顺序无关」条款同机制。→ E102-06/07（及 R1-b 的 E102-09）的精确分野是 #5 已交付的能力，非 #8 新增。

**推论**：矩阵全绿不是「SA6 运气好」，而是 #5 架构的**演绎必然**——若矩阵出现红灯，反而说明 #5 违反了自身设计（判定顺序漏映射或递归路径断裂）。SA6 中断门禁声明（简报 §六.3）的判定「验收测试写出来就是绿的 → 功能已存在」在架构层面成立：**被验证的行为自 #5 合入起即完整存在，#8 的增量只是把它从单点负例扩展为成对矩阵的验证资产**。

**R1/R4 修订注记（推论的边界）**：「演绎必然」论证的是**行为正确性**（每单元格的码与锚点可由规范+实现推导），不蕴含**覆盖完备性**——同一规范条款映射到多个实现代码位时（E103 的两个分支），只采样其一的矩阵对该条款的防护是单边的（删另一分支全绿通过，SA2 攻击点 #2 正是击中此处）。首轮 §5 G3 将其裁为「非阻塞」与 E105 双分支各有单元格的处理标准不一致，本修订纠正：G3 升级为基线工作项（§5）。同理，攻击点 #1 表明「全绿」也不蕴含「槽位语义合规」——绿灯只证明断言与行为一致，不证明断言形态配得上它的名字；这就是 R3 方法论补丁的由来。
