## 2. 逐项详述

### 2.1 R4-1（MEDIUM）契约行常数内嵌 m 而行条件不冻结 m——「最坏同排满」第三次失守

四审点名的核验命题是「契约口径最坏化后合计保守界 ≤ WORK_LIMIT 在最坏同排满下成立」。合计行自身的算术成立（188,004,800 = 各行上限之和，6% 余量，我方复算吻合），但**「各行上限」在行自己冻结的条件下不是真上限**：

- **T1 行**。乘法链第一层写明「单次 Pattern 应用成本上界 = T1 类 64 码元 × **m≈135** × f=3 ≈ 2.7×10⁴」——m≈135 是 AssetId 类的例示；行条件列冻结的却只有「单次输入 ≤ 64 码元、≤ 5_000 次」。输入长度不约束 m：`[a-z]{1,64}` 是 64 份 Class+Split 展开（≈127–135 指令），**多连拼即线性放大 m**，八连 ≈ 1,016、十六连 ≈ 2,032，全部 ≪ 程序规模上限 10_000、全部前瞻-free、全部合法子集内。每应用定理界 = (64+2)×m×3 = 198m，与输入长度同为行条件却不受行条件约束。饱和攻击：5,000 键 × 64 码元非匹配值（`'a'×63+'!'`，探索量最大）→ 全局计费 5,000×198m；**m ≥ 149 即破 2×10⁸**。这不是刀锋构造：§6.4 包络表「T1 包络上限（保守定理界 f=3）**m ≲ 340** 且 len ≲ 2.5K」白纸黑字放行 m 至 340——该表口径下 2,184 次应用即触顶，而契约行允许 5,000 次。两个 R3/R4 表在最坏同排满下**互斥**。
- **T2 行**。行条件冻结了 `L·m_sub·f_sub ≤ 15`（前瞻负载——R3 轮已做对的那个常数），但 T2 定理是 `(len+2)×m×f + L(len+1)(len+2)m_sub f_sub`，**外层主程序的 m·f 项同样未入条件**：m=10_000、len=256 时每应用 = 258×(30,000+3,855) = 8.7×10⁶，× 50 = 4.4×10⁸ 破契约；行常数 10⁶ 隐含 m≈8。同一修法：条件补全或改冻单次定理界。
- **编译孤儿行**。计费表第 3 行「正则编译一次 = 编译产物指令数」是五类计费点之一，契约表五行（应用×2 + 事件 + preview）没有一行承载它。「合计 = 各行上限之和」作为精确断言漏一项：≤ 5,050 个 distinct 模式 × 135 指令 = 6.8×10⁵（regexCache 使同模式只编译一次，故上界为 distinct 数 × m——修 R4-1 后 m ≤ 135 代入即可）。数值上 188,686,550 ≤ 2×10⁸ 被 6% 余量吸收，但推导须声明而非默认。

**为什么是 MEDIUM 而非 LOW**：与 R3-2 完全同构——运行时安全（全局预算 loud 兜底、~1s、fail-closed，我方确认）、旗舰安全、不产生错误校验结果；被证伪的只有「契约内调用必在预算内」这一**冻结承诺**的推导完整性。而这正是 R2-2 → R3-2 → 本轮连续三轮的同一病灶（乘法/口径没做全：R3-2 补了跨行乘数与 preview 口径，R4 重排后又漏了行内常数的 m 前提）。契约表是 §5.7-3 的核心交付物、SA4 验证设计的直接输入，行条件不自洽即不可用作充分条件。修法 2–3 行，不动任何数值冻结面（WORK_LIMIT、5,000/50/3×10⁶ 行值全部可保留——只补条件从句）。

### 2.2 R4-2（LOW）「≤ 4M 槽 ≈ MB 级」量纲标签

R3-1 的修订主体（稀疏类型签名 + 稠密预分配禁令 + 附录 8 SA4 锚点）有效且字面成立（§3 核验）。失准的只是随修订新写的效果句：槽位上界按「每槽写入前必已付出 ≥ 1 计费步」推出 ≤ 4M，但每槽实际 ≥ 2 步（外层闭包访问该 Look 指令 1 步 + 锚定子模拟 ≥ 1 步——空前瞻子程序 `(?=)` 的闭包也要访问 Match 1 步），故 ≤ 2M；再乘 Map 条目 24–48B 得 48–96MB 最坏峰值，可达构造在案（§0）。「无 GB 面」成立，「≈ MB 级」不成立。修一句；不修也不改变 R3-1 的落实判定，但 SA4 若照字面设计「MB 级」内存断言会得到误阈值，故入清单。
