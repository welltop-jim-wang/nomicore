## 1. 缺陷链 A：建流前创建结局被无归属通道确定性丢弃

### 1.1 机制链条（代码锚点）

1. Registry 构造期经 `createCreateDiag(options.diagnosticLog, clock)`（`packages/namespace-registry/src/registry.ts:776`）捕获 seam 的**共享 emitter** `diagnosticLog.emitter`（`packages/namespace-registry/src/create-diagnostic.ts:310-341`——构造期一次读取，此后 emit 只用该引用）。
2. `initStream` 之前的全部槽内早结局经共享 emitter 发射：
   - `registry.ts:1316` input-snapshot 拒绝（`emitEarlyOutcome`，clock 读数在槽内 Clock 步之前）；
   - `registry.ts:1328` prepare 期 schema-compile / validation 拒绝；
   - `registry.ts:1364`、`registry.ts:1394` create-document-internal fatal；
   - `registry.ts:1411`（DocCreateOperationalError → `NAMESPACE_CREATE_FAILED`）、`registry.ts:1419/1427`（DocCreateFatalError / unknown → fatal，committed 事实保留）；
   - 公共入口同步段的停接纳 / identity 拒绝（`registry.ts:1933/1943`）——此二者发生在 namespaceId 生成之前，本就无归属可用（非本缺陷链对象）。
3. 生产供应方 `apps/yjs-server/src/diagnostics.ts` 把该共享 emitter 实现为**无归属通道**：L74–76 `unattributedEmitter = { emit: () => drop('unattributed') }`，L114–116 `binding.emitter = unattributedEmitter`——恒丢弃 + 计数（NDJSON `diagnostic-log-emission-dropped`），「绝不伪造归属」（该文件头注释自述：*全部 initStream 之前的 create emission 落此通道*）。
4. 语义 emission 面无 namespace 字段（`packages/namespace-diagnostic-log/src/emission.ts:33-51`）；归因唯一载体 = **哪个 emitter 实例接收**（#155 数据键控归因）。数据键控通道 `runtimeEmitterFor(namespaceId)` 只被 initStream 之后的路径消费：`emitStreamOutcome`（`registry.ts:1450/1463`）与 Runtime factory 第三参（`registry.ts:1440`、open `registry.ts:1229`）。**建流前结局没有任何数据键控通道可走。**

- CONTEXT.md「变更尝试」（L148–150）：「被拒请求也属于变更尝试，即使它从未读取输入或进入 transaction」。

## 2. 缺陷链 B：同步日志 I/O 位于业务关键路径

### 2.1 B1：create lifecycle carrier 槽内（建流 + 同步 append）

- `registry.ts:1436` `diag.initStream(id.namespaceId, state?.slice())` 位于 `runCreateAttempt` 槽内（Persistence createDoc 成功后、factory 之前）。生产供应方 `initStream` → `ensureAdapter` → `createFileDiagnosticLog` 构造器**同步 fs**：recursive `mkdirSync`、manifest `'wx'` 不可变创建、genesis append、`current.json` temp+rename（`packages/namespace-diagnostic-log/src/adapters/file.ts` 文件头契约），含 #153 reopen 健康证明/可证明尾部修复与 #154 构造期 retention sweep（`sweepOnOpen` 缺省 true，file.ts:1455–1460）。
- `registry.ts:1450`（#17 committed）/`registry.ts:1463`（#18 fatal）`diag.emitStreamOutcome` 同样在槽内，经 ns emitter `emit` → 每 record 独立 `appendFileSync`（file.ts:16–17 引入、684/699 落盘点；无队列/batch/fsync——首切片形态）。
- **复现（T8，慢建流 120ms + 慢 append 120ms）**：事件序 `[0] initStream:start → [1] ensure:start → [2] ensure:end → [3] initStream:end → [4] emit:start → [5] emit:end → [6] create:settled`——红灯断言 `create:settled(6) < initStream:end(3)` 失败（`expected 6 to be less than 3`）；墙钟旁证：create() 结算 ≥ 240ms。业务结果 GREEN（ok lease）。
- **复现（T9，慢建流 200ms + 已接纳 create + shutdown）**：`shutdown:settled(6) < initStream:end(3)` 失败——shutdown 等待已接纳 create 终局（ADR-0009 L97–101），而建流在槽内，故 shutdown 被日志存储同步延长（墙钟 ≥ 200ms）。

### 2.2 B2：open lifecycle 槽内 adapter 构造（reopen/repair/retention sweep）

- `registry.ts:1229` open 槽内 factory 第三参 `resolveRuntimeDiag(identity.namespaceId)` → `runtimeEmitterFor(ns)` → 缓存 miss 时构造 File adapter——locator 解析、reopen 健康证明、尾部修复 truncate、构造期 retention sweep 全同步 fs。diagnostics.ts 头注释自认落点：「构造期同步 fs……只发生在 Registry open/create/import 槽内（write sequencer 尚不存在——#153 纪律合规落点）」——但 #153/ADR-0012 amendment 的隔离条件针对 **namespace 生命周期业务关键路径**整体；Registry lifecycle carrier（ADR-0009 L32 同 key 串行 / L62 槽内清单）同样是任务要点名隔离的关键路径（任务简报 AC3）。
- **复现（T10，ensureBlockMs=150）**：新 Registry 实例 open 已存在 namespace → 事件序 `[0] ensure:start → [1] ensure:end → [2] open:settled`——红灯断言 `open:settled(2) < ensure:end(1)` 失败；open() 结算被 150ms 构造延长。业务面 GREEN（open 成功）。

### 2.3 B3：Runtime write-sequencer 槽间窗口的同步 emit

机制（微任务序，已用纯序模拟独立验证 + 真实 Runtime 复现）：

- `packages/namespace-runtime/src/sequencer.ts:38-42`：`enqueue` 内 `this.tail = settled.then(noop, noop)`（noop hop 先注册）；公共方法随后在 `settled.then(...)` 注册 `emitSlot`（`runtime.ts:469-475` 等 8 处）。
- 槽 N 的 settled 履行时微任务队列序为 `[C1(noop), C2(emit)]`；下一槽 N+1 的 run 挂接在 noop hop 之后，C1 完成才排程——**emit 恰落在「本槽释放 → 下一槽启动」之间的关键窗口**：同步 `appendFileSync` 的延迟/挂起直接推迟下一业务槽启动、close barrier 推进与 shutdown 排空。
- #149/#151 注释宣称「emitSlot 由公共方法的 `.then` 回调调用——write sequencer slot 已释放之后（设计 §7.1 微任务序证明）」：该证明只覆盖**相对上一槽**，未覆盖**相对下一槽**——emit 位于链尾 hop 之前，仍在 sequencer 关键路径上（下一业务写必须等它）。ADR-0012 amendment L250 的合规条件在「不延长业务排序关键路径」意义上未满足；ADR-0011 L129「adapter 慢、失败或队列满都不得延长 write slot 或阻塞 close/shutdown」被违反。
- **复现（T12，慢同步 emitter 100ms）**：两次 `mutateData` 顺序提交——墙钟旁证：w1→w2 结算间隔 **103ms**（`expected 103 to be less than 50`）；顺序红灯：`notify:2`（下一业务槽体 S6）必须先于 `emit1:start` 的断言失败（实际序 `notify:1 → emit1:start → emit1:end → notify:2`）。业务面 GREEN（两写 ok、终值正确、FIFO 不变）。
- **复现（T13）**：在途写 + 立即 `close()`——close 结算 **101ms**（`expected 101 to be less than 50`）；顺序红灯：`close:settled` 晚于 `emit1:end`（emit 位于 close barrier 推进之前）。

### 2.4 契约依据（缺陷链 B）

- ADR-0012 amendment L250（规范性接线条件）：「任何将 File adapter 的 `emit` 接入 namespace 生命周期的调用点，必须位于 NamespaceRuntime write sequencer slot 之外，或在该 slot 已释放之后；不得在 slot 内执行同步 File adapter `emit`。不满足该条件的接线为不合规，必须由……后续接线票修复」——**本任务即该票**；amendment L248：「『有界』……不表示底层文件系统延迟有时间上界，亦不表示 `emit` 可在任意调用点不阻塞」。
- ADR-0011 L20/L129（隔离与 shutdown 上界）、L123（日志不得引入第二个业务排序机构）、L127（committed 事实后 emission、emitter 不被 await）。
- ADR-0008 L51（slot 定义：lifecycle/fatal gate → writable gate → 快照 → 校验 → 单事务 → `await notifyDirty()` → 释放——不含日志 I/O）；ADR-0009 L62（create 槽内清单不含建流）、L32（carrier 串行）、L97–101（shutdown 公共契约）。
- 任务简报 AC3（建流、reopen/repair、retention sweep、同步 append 不在业务关键路径）/ AC4（慢或挂起存储不阻塞下一业务槽、不无限延长 create/shutdown）。

### 3.3 判据设计说明

- **顺序断言为主判据**（确定性，免定时器抖动）：以事件迹 `indexOf` 比较「业务结算标记」与「日志存储完成标记」；修复后（接线移出关键路径 / 延迟或队列化）业务结算标记先行。

## 5. 给下游 SA 的红线与敏感点（登记，非裁决）

1. **seam 字段名冻结**：红灯锚定 `diagnosticLog.emitter` / `initStream` / `runtimeEmitterFor`（Registry）与 `diagnosticEmitter` + `clock` 成对（Runtime）——修复不得漂移字段名（SA8 红线 7）。
2. **emitter 公共 seam / record schema / manifest policy / 词表冻结**（SA8 红线 1/4）：早结局补记不得新增 operation/stage/result 值；补记记录保持自身 observedAt/attempt 语义，不得冒充 genesis 或伪称重放连续（ADR-0012 L24；SA8 红线 5）。
3. **早结局归属通道形态**是核心设计点：Registry 已持有候选 namespaceId，但语义 emission 无 ns 字段、归因=接收实例——扩展数据键控消费点（如 `emitOutcome` 携带 ns 走 `runtimeEmitterFor`）或 Host 侧按候选 ns 缓冲，均为可行方向；被拒 create 无后续 stream 可补记 ⇒ stream 须为该结局建立（T11 红灯锚的落点）。id 耗尽 fatal 的归属（无可用 ns id）需显式裁决。
4. **隔离载体形态**（`_relevant_decisions` §设计敏感点 1）：slot 外延迟同步 append vs queue/batch 切片（后者须另行定义 close/shutdown、flush、队列满、fsync 四类语义——ADR-0012 L252）。注意 T9/T13 的顺序断言要求日志 I/O 的排程**不先于** shutdown/close 结算续段——微任务级 deferral 不满足；须 macrotask/queue 级搬移或异步化。
5. **shutdown 公共契约不变**（SA8 红线 6）：同 Promise、`NamespaceRegistryShutdownError` 聚合、停止接纳；日志 drain 只能是有界 best-effort。
6. **不得引入第二个业务排序机构**（ADR-0011 L123）：emit 接收时点变化不得产生新的业务顺序语义；notifyDirty 槽序不包裹不替代（L128）。
7. 既有 #150「恰一条最终结局」裁决与候选重试零发射现状（§1.5）如需演进（duplicate 结局可诊断），属词表/契约演进面，须过设计评审——本复现未预裁。

### 9.3 B3 槽间窗口机制本轮独立重推导

`WriteSequencer.enqueue`：`const settled = this.tail.then(run, run); this.tail = settled.then(noop, noop)`——下一业务槽的 `run` 挂在 `settled` 之后再经一个 noop hop 的 `this.tail` 上；而 `runtime.ts` 公共方法把 `emitSlot` 挂在**裸 `settled`** 上（`void settled.then(...)`）。两条链都从 `settled` 出发，但 emit 回调先注册于 `settled` 本体，下一槽 `run` 排程于 `settled.then(noop)` 之后——同步慢 `emit`（File adapter `appendFileSync`）因此先于下一槽启动执行，落在「本槽释放 → 下一槽启动」关键窗口内。T12/T13 红灯（下一槽推迟 101ms / close 延长 101ms）与该推导一致；close barrier 同经 `sequencer.enqueue` 排于尾后，同理被推迟。
