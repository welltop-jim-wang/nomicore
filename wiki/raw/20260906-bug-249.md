## 1. 缺陷链 A：单飞竞态——调度门只有 running 态（AC1）

### 1.1 机制（代码锚点，`packages/namespace-registry/src/diag-pump.ts`）

- L83 `const draining = new Set<string>()`——泵**唯一**的调度状态载体，语义为「该 ns 的 drain 回调**正在执行**」：
  - L107 `draining.add(ns)` 在 `drainNamespace` **回调体内**才执行；
  - L117 `finally { draining.delete(ns) }` 回调结束时清除。
- L134–140 入队侧调度门：`if (!draining.has(namespaceId)) { setImmediate(() => drainNamespace(namespaceId)) }`——**没有任何结构记录「已 scheduled 未执行」**。
- 因此存在一个**burst 窗口**：从第一个任务入队（排下 S1）到 S1 回调实际触发（check 阶段）之间，`draining` 恒为空，窗口内每个被接纳的入队都再排一个 setImmediate。
- 窗口成因（生产时序）：入队点位于 Registry lifecycle carrier 槽内与 Runtime write-sequencer 槽间窗口（`create-diagnostic.ts` 路由三态），业务结算经微任务续段推进，check 阶段要等当前宏任务链让出事件循环才到来——同步长链（多 create 编排、慢同步 I/O 段）期间同一 ns 可积累多个诊断任务。
- L128–132 的次序放大了一个事实：**容量早退在调度语句之前**——`queue.length >= 256 → return` 先于 `setImmediate`。故单窗口重复调度数 = 该窗口被接纳任务数（≤256），而非入队总数。

### 1.2 复现结果（`.scratch/249/repro-pump.test.ts`，确定性手工调度器：替换 `globalThis.setImmediate` 为记录器，零真实定时器）

| 用例 | 场景 | 实测 | 期望（AC1） | 判定 |
|---|---|---|---|---|
| R1a | 同一 ns 同步 burst 1000 条 emission | `schedules=256`（队列接纳前 256 条各排一个 drain） | `1` | 红 ✓ |
| R1b | 同上后排空全部回调 | `fired=256`（255 个空转 drain）、`delivered=256/1000`（744 条被容量早退静默丢） | `fired=1, delivered=1000` | 红 ✓ |
| R1c | 同步 5000 条入队 | `pending=256` 个待触发的重复 drain、4744 条被丢 | `< 50`（每 ns 待处理 drain 应有界趋近 1） | 红 ✓ |
| R1d | drain **运行中**经 Host emit 重入入队 | `schedules=1`，重入任务被运行中循环当场消费 | 同左 | 绿对照 ✓ |

量化结论：单 ns 单 burst 窗口浪费宏任务 = 接纳数 − 1（上界 255）；持续运行下 drain 调用次数与接纳任务数 1:1（理想为每窗口 1 次）；跨 ns 全局待处理重复 drain 上界 = 256 × 活跃 ns 数。**业务面零影响**（drain 全在业务路径外、全同步非抛）——缺陷纯粹是事件循环任务放大与资源有界性（AC1「至多一个 scheduled/running drain」的直接违例）。

### 1.3 与 #226 设计的偏差（规范锚）

`wiki/raw/task_issue-226_design.md` §L112–114 冻结的泵结构语义：「入队后若该 ns 未在 drain，则 `setImmediate(drainNs)` **一次**（单飞：drain 中重复入队只补一次调度）」——设计意图的 `draining` 是覆盖 **scheduled+running** 的单飞位；实现将其窄化为 running-only 集合，scheduled 态无人记录。这是实现与设计冻结条款的偏差，非设计缺口。

## 2. 缺陷链 B：满队列丢弃零上报（AC3）

### 2.1 机制

- L78 `DIAG_PUMP_MAX_QUEUE_PER_NAMESPACE = 256`；L128–132 满队 drop-newest——**丢弃策略本体正确**（丢新保旧、保留已排队顺序；R3a 实测 delivered 依序为第 0–255 条）。
- L129–131 注释自述「静默（无 Registry 侧健康通道——健康面归 Host/adapter 独立 observer，Registry 不代发）」——该立场源自 #226 设计（wiki 历史证据，非规范契约，冲突报告 §检查范围 L17 已裁定）；ADR-0011 L25（「实现应尽力上报 dropped count、sink failure 和 queue health」）与 ADR-0014 L240（「按 operation/reason 增加低基数 dropped metrics，并走独立 observer」）构成现行为未兑现的上报义务。
- **结构性沉默**：`DiagPumpDeps`（L60–65）只有 `initStream` 与 `resolveEmitter` 两个依赖面；泵构造期不接收 observer/health sink，丢弃点不产生任何可观测副作用。R3b 实测：Host 可见信号共 512 个（256 resolve + 256 emit），**全部属于已投递记录；44 条被丢记录对应零信号**。

### 2.2 与缺陷 A 的叠加伤害

burst 窗口内队列容量是**投递吞吐上界**：R1b 中 1000 条诊断只投递 256 条、744 条无痕蒸发。诊断虽是 best-effort（ADR-0011 L23 允许丢失），但「允许丢失」≠「必须不可知」——L25 的上报义务正是为了让丢失可计量。修复后 drop 计数必须走既有低基数语义（ADR-0009 L95 内部结构化 observer seam；label 仅 operation/reason 等封闭维度，namespaceId/streamId/token 不得入 label——ADR-0010 L159、ADR-0011 L87、ADR-0014 L240），且**不得为记录 drop 再占用同一队列**（ADR-0014 L240）。

## 3. AC2 防丢失不变量：现实现成立（4/4 绿对照），属修复守护锚

### 3.1 静态论证（为何现实现丢不了已接纳任务）

`drainNamespace`（L106–119）**全程同步、无 await 点、无 Host 可插入的让渡点**：

1. 循环每轮 `queues.get(ns)` 重取引用（L110）——drain 任务执行期（`runTask` → Host `initStream`/`emit`/resolver）的**重入入队**落到同一数组，被同轮循环继续消费（R2b 实证：末任务期重入 2 条全部投递，`schedules=1`）；
2. 空队判定（L111 `shift() === undefined`）与队列删除（L115）/draining 清除（L117）之间无任何 Host 代码可运行——「排空后清理与入队交错」窗口在同步执行下不存在；
3. 非 running 态的入队恒补一次调度（L134）——队列非空 ⇒ 必有 ≥1 个待执行或可补的 drain；
4. `runTask` 逐任务 try/catch 收编（L85–102）——违约只废单条记录，不阻断队列（R2d 实证）。

### 3.2 探测的交错族（R2a–R2d，全绿）

- stale 重复回调夹在两次活 drain 之间（空转 no-op，不吞任务；R2a：`[0001,0002,0003]` 全投递且 FIFO）；
- 回调间入队（stale 回调先行触发、新调度的回调随后收尾；R2a）；
- 末任务执行期 Host 重入（emit 内再入队 emission + init-stream；R2b：`initStreams=[{genesis:false}]`、投递序 `[0020,0021]`）；
- init-stream 与 emission 混合的 per-ns FIFO / 建流先于对应 emission（R2c：`genesis:true` 先行）；
- resolver 违约 / emitter 同步 throw 只废当条、队列照常排空（R2d）。

### 3.3 结论与修复风险面（给 SA1/SA6 的非预裁输入）

- **判定**：AC2 在 PR #248 现实现不可达丢失——Issue 文中「特定交错下丢失已接纳 emission」的缺陷域在本 HEAD 上的实际形态是 §1/§2（重复调度 + 静默容量丢弃），而「stale callback/队列删除/scheduled-running 状态竞态」是 **AC1 修复的最大回退面**：典型坏修复（如单飞位在循环空判后、Host 重入消费前清除；或循环外缓存队列数组引用后重入建新数组而旧循环仍在旧数组上空转）会立即引入真实丢失。红→绿契约必须把 R2a–R2d 四交错作为回归锁纳入（AC7「stale interleave 不丢任务」的红灯在现实现不可达——应以其**持续绿**为修复后验收形态，另以人为制造的状态机坏形（如清除时序错位）验证测试的判别力）。

## 4. 缺陷链 C：collision / `DOC_DUPLICATE` 候选结局零诊断（AC4）

### 4.1 机制（代码锚点，`packages/namespace-registry/src/registry.ts`）

- 生成式 create 编排（L1268–1284）：每候选 `generateNamespaceId` → `admitCreateAttempt` → 槽内 `runCreateAttempt`。
- **entry collision**：L1311 `if (entries.has(id.key)) return { kind: 'retry' };` ——直接返回重试，**零诊断发射**（无 emit、无建流、无 observer 代偿）。
- **Persistence duplicate**：L1408 `await persistence.createDoc(...)` 的 catch 内 L1410 `if (cause instanceof DocDuplicateError) return { kind: 'retry' };` ——同样**零诊断发射**。
- 两处均有 L1248–1254 注释自辩：「诊断日志恰为被接纳的公共 create 发射一条最终结局；表达候选重试需要冻结 v1 词表之外的 retry result/correlation 形状」。该立场与 ADR-0011 L57 冲突——「namespace create，**包括输入、schema、ROOT、duplicate、Persistence 与 post-commit Runtime construction 结局**」是明文覆盖要求；且「每候选 = 一次独立 namespace-create 变更尝试（CONTEXT.md L148–150：被拒请求也属变更尝试）」在冻结词表内**完全可表达**，无需 retry 形状发明（见 §4.3）。
- **重试预算耗尽**：L1269–1273 `throwIdGenerationFatal`（L818–825）仅发 observer 事件（`create-id-generation-failed`），零诊断；终局无可用候选 id，归属是设计决策（#226 §1.5 已登记未预裁）。

## 5. 既有绿灯基线为何零感知（防复发面）

诊断相关 5 套件在 HEAD 全绿（`registry-issue-226-red`(13)、`registry-create-diagnostic-red`(16)、`registry-create-diagnostic-code-source`(6)、`registry-create`(47)、`registry-surface`(12)，共 **94/94**，Duration 33.8s）：

- #226 契约全部为**到达型 poll**（`expect.poll` 等 storage 标记出现）+ 顺序锚——不计数调度次数、不制造 burst 窗口（单 create 的诊断任务数远小于 256）、不探测容量与丢弃；
- duplicate 族在 #226 SA1 报告 §1.5 仅「登记未立红灯」（当时按 #150「恰一条最终结局」冻结裁决豁免）；Issue #249 把该豁免推翻（ADR-0011 L57 优先）；
- 泵的 `DiagPumpDeps` 无健康面 ⇒ 任何既有测试都无从断言丢弃可见性。

AC7 要求的新红→绿契约须覆盖（本轮复现已给出可固化形态）：burst 只调度一次（R1a 型，确定性手工调度器或可计数 fake check 阶段）、重复回调空转不吞任务（R1b/R2a 型）、queue-full 丢弃 + 健康上报（R3a 型——断言新健康信号本身，而非本报告的「零信号」反向形态）、collision/duplicate/retry 成功/耗尽（T-A/T-B/T-C 型）、异常隔离（R2d 型 + initStream throw），且证明 PR #248 实现失败（本轮 6 红已证）。

## 6. 业务不变量确认（缺陷纯诊断面）

复现全程业务面保持冻结语义：8 次重试预算与候选再生成（T-A/T-B `createCalls` 序列精确为 [碰撞候选, 胜出候选]）、成功重试恰一条最终 create 结果（T-A/T-B 胜出 ns 各恰 1 条 committed 记录 + 1 个 lease）、耗尽 `committed:false` Registry fatal（T-C）、`DOC_DUPLICATE` 判定不覆盖已提交内容（StubPersistence 未收第二次同 id createDoc）、create 返回值/提交事实/顺序零变化（泵全部 O(1) 入队、drain 业务路径外）。与 ADR-0011 L20/L23 隔离义务一致。

## 8. 给下游 SA 的修复方向输入（非约束，最终以 SA1 设计 + SA2 评审为准）

1. **单飞状态机**：以显式 scheduled 位（或 `scheduled/running` 合一标志）覆盖「已排未执行」窗口；位清除时序必须保证「drain 决定退出前最后一次队列空判」与「位清除后首入队补调度」无缝衔接（§3.3 坏修复形态即为其反例）；保持 drain 全同步非抛与每轮重取队列引用的既有结构。
2. **健康上报**：经 ADR-0009 L95 既有内部结构化 observer seam（不新增公共 API/事件——L107–114 公共面冻结）；drop 计数低基数（operation/reason 维度）；不为记录 drop 占用同一队列（ADR-0014 L240）；泵满静默丢弃的 #226 历史立场按冲突报告 §17 裁定让位于 ADR-0011 L25 上报义务。
3. **词表路径**：优先既有冻结词表表达（§4.3 表）；若 SA1 判定需无损性更强的形态（如 attemptId 关联候选链），须走完整演进通道（schema `@2` + 新 generation + `test/schema-freeze.test.ts` 指纹钉死 + 设计评审 + CONTEXT.md 同步），v1 不写 `result:'unknown'`。
4. **归属与建流**：collision/duplicate 归既有 namespace 流；与 `streamedNamespaces` seed 交互注意「已建流不重建、未建流 genesis-less 补建一次」（ADR-0014 L22）；建流/投递仍全部走泵（业务槽外 macrotask）。
5. **静态守卫**：修复不得引入被 registry-surface 三正则拦截的裸 `setTimeout`/`setInterval`/`Date.now`（`setImmediate` 为 R4 注释契约显式许可原语）；不得触碰 adapter 存储语义（ADR-0014 amendment L250/L252——泵不是 writer queue，单 record 同步 append 不变）。
6. **红→绿契约**（AC7）：以本报告 §5 所列形态固化；R2a–R2d 四交错必须作为「修复后持续绿」的回归锁纳入；burst 计数断言需确定性调度器（手工 check 阶段或可计数 fake），避免到达型 poll 对调度次数的结构性盲区。

## 9. 结论

- Issue #249 的三条缺陷链（AC1 单飞竞态、AC3 静默丢弃、AC4 duplicate 诊断缺位）在 HEAD `ac91a6b` 全部可执行复现且仅存在于诊断面（业务不变量零损伤）；AC2 防丢失不变量现实现成立，属修复守护锚。
- 与 ADR 全集无冲突（承 SA8 前置门禁 clear 结论；本分析未发现任何需要演进规范才能修复的阻断点——既有冻结词表足以承载 AC4）。
- 无需冲突复检（requiresConflictRecheck=false）：修复路径均落在 ADR-0011/0012/0009/0010/0006 既有条款的兑现域内。
