## 2. 逐项详述

### 2.1 R2-1（HIGH）§6.4 定理对前瞻不成立——合法值误拒类缺陷回归

**攻击构造**（子集内、ECMAScript 合法，实测 `/ (?=.*;)z/.test('xxxxxz;') === true`）：

```
type ROOT = { name: string & Pattern<"(?=.*;)z"> };
快照 { name: 'x'.repeat(N) + 'z' + ';' }     // 真值：匹配（pos N 处前瞻命中、z 命中）
```

模拟行为：非锚定搜索每轮重播种 `{start}` → 闭包每轮处理 `Look` → 从 pos 起**锚定**子模拟 `.*;`（扫描到尾部 `;`，成本 ≈ 15×(len−pos)，m_sub≈5、f=3）→ 外层消耗 1 字符后再重播种。总成本 ≈ Σ 15×(len−p) ≈ **7.5·len²**。预算 `1024·len + 16384`：令 L=len，7.5L² > 1024L + 16384 ⟺ **L ≳ 151**。

**后果**：~152 字符以上的合法值 → 单匹配预算耗尽 → 「Pattern 匹配步数预算耗尽…无法判定」→ `ok:false`。定理声称的界 (len+2)×m×f = 154×8×3 ≈ 3.7×10³，与实际 ~1.8×10⁵ 差 40+ 倍——**定理陈述为假**。锚定写法（`^(?=.*d)[a-z]+$`，密码式惯用法）只在前导 pos 评估一次 → 线性、安全；出事的是**非锚定 × 前瞻内含 `.*`/`{n,m}`** 类。预算确实兜住了运行时（不挂死——这点比 R1 强），但 §6.4 的两条支柱陈述失实：

- 「耗尽 ⟹ 该乘积（m×len）超出包络」——假（本构造 m=8、len=250 时乘积微不足道仍耗尽）；
- 包络表「合法包络上限（定理界下）= m ≤ ~340 且 len ≤ ~2.5K」——对含前瞻模式不成立。

**红灯影响**：`(a+)+$`、`^[a-z]{2,4}$`、AssetId 均无前瞻 → §6.6 对账仍成立，红灯面不受影响（须成文）。

### 2.2 R2-2（HIGH）§5.7-3 包络标定没做乘法——旗舰场景规模即触顶

用**设计自己的数字**推演（§6.4 表：AssetId m≈135，64 码元键 ≈ 135×66×3 ≈ 2.7×10⁴ 步）：

- §5.7-3：「带 Pattern 的常规快照 ≤ 10⁴（含 NFA 模拟步）」——**单个** 64 字符 AssetId 键的保守界已是 2.7×10⁴，超「常规」上限 3 倍。两节数字互相矛盾。
- Record 键乘法：16M ÷ 2.7×10⁴ ≈ **590 键**触顶（保守界）；按可选链展开的实际状态集宽度（每轮 ≤ 64 态、单键 ≈ 5~7×10³ 实际步）≈ 2500~4000 键。**数千资产的全合法快照**（迁移后体检的真实规模）→ `WorkBudgetExceeded` → `ok:false`。
- 联合乘法：R2 删短路后 `distances = members.map(countIssues)` 对全部成员完整计数、段 2 接受判定在 map 之后（接受也不省工作）→ 成员内的 Pattern 工作量 × N。
- 「16M 单位 ≈ 数十万节点访问级」的等价表述掩盖了 NFA 步与节点访问 1:1 计费：真实含义是「总计 ≤ 16M 单位 ≈ 600~4000 次 Pattern 应用或数十万节点访问」——对 Pattern 承载快照错 1~2 个数量级。

机制本身（charge + memo + loud，R1 #1 的 CRITICAL 挂死）**成立且已兑现**；不成立的是第 3 层「合法调用不触发的包络」的论证——它是单点标定，不是组合包络推导。

### 2.3 R2-3（MEDIUM）计费表的三个未覆盖热点

1. **封闭对象未知键扫描**：`for k of Object.keys(value) where fields 无名 k` —— 未知键不进 validateValue；键名匹配若线性扫 fields 则每键 O(#fields)。10⁸ 键快照（调用方已持有）→ 未计费 O(键数×字段数) 纯遍历，`ctx.work` 几乎不动，预算形同虚设。
2. **emit / overflow 记账**：不在计费表。上例 100 条之后的 overflow++ 循环完全免费。
3. **preview**：`JSON.stringify(value)` 截断至 40——若先 stringify 后截断，是对大值的未计费 O(值规模) 序列化，≤100 次 emit 可放大百倍。

三者都不产生挂死级风险（成本仍 O(快照规模)，调用方为快照本身付过同阶成本），但直接证伪 §5.7-2 的「计费点全覆盖…构造性成立」与「无识别面即无漏报面」——修法便宜（键/元素访问计 1；preview 有界化），应堵。

### 2.4 R2-4（MEDIUM）§6.2 新冻结表内部矛盾 + 一处与 ECMAScript 相反的断言

见 §0 实测。三件事：

1. `\uZZ` 的处置两行相反（字面量行：IdentityEscape 'u'；IdentityEscape 行：保留前缀+非完整形 → loud）——SA3 无唯一权威，正是 #8 类「走样素材」的复发。
2. IdentityEscape 行以 `\x` 非完整形为 loud 例——实测 `/\xZ/.test('xZ') === true`（Annex B IdentityEscape）。要么对齐基线，要么两行一致地声明「有意收紧」，不能一行对齐一行收紧。
3. 「`\u` 后 `{…}` 按 Annex B 非量词字面量」与实测相反（`/\u{2}/.test('uu') === true`：`{2}` 是作用于字面量 `u` 的量词）。按设计字面实现会把 `Pattern<"\u{2}">` 的接受语言从 `'uu'` 变成 `'u{2}'`——双向偏离。

零 fixture 自伤（fixture/红灯三个模式都不含这些构造），但 §6.2 是 R2 以「枚举完备、无自伤」为验收新冻结的表，须自洽。
