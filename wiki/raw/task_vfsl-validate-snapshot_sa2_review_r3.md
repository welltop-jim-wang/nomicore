## 2. 逐项详述

### 2.1 R3-1（MEDIUM）lookMemo 稠密分配面——「无 GB 面」的字面读法失效

构造细节：模式 `(?=)(?=)…(?=)`（200 个空前瞻顺排，ε 相连）编译为 Look₁→Look₂→…→Look₂₀₀→Match，全部在初始闭包内一次可达。每条 Look 的子程序仅 `[Match]`，求值成本 O(1)。对 10⁷ 码元输入：

- 初始闭包触碰 200 条 Look，每条：查 `lookMemo[该指令][pos]` 未命中 → 锚定子模拟（~2 步）→ **写回**。写回即创建该指令的 memo 槽容器——若容器按声明类型实现为 `boolean[len+1]`（`new Array(10_000_001)` 或 `new Uint8Array(...)`），一次物化 10⁷ 槽；
- 闭包抵达 Match（空匹配）→ 返回 true。全程计费 ~600 单位，匹配**成功**且瞬时；
- 内存：200 × 10⁷ = 2×10⁹ 槽（普通 JS 数组 ≈ 8B/槽 → 16GB；Uint8Array → 2GB）。分配不是 §6.3 定义的「闭包访问/转移/lookMemo 命中」任何一类计费步——单匹配预算（4M）与全局工作预算（2×10⁸）对该面**双失明**；V8 OOM 是不可 catch 的进程级 FatalError，§2.2 崩溃边界（E100）收编不了。

设计现有的守卫句「每槽写入前必已付出 ≥1 计费步的求值 → 总槽位被步数预算封顶」本身是对的——但它只对**写时物化**的存储成立；声明的类型签名 `boolean[len+1]` 恰好邀请相反的实现。SA3 逐字实现规约（附录第 8 条要求 lookMemo「不得省略」）时，最自然的落码就是稠密数组。修法一句话：存储形式定为稀疏（`Map<Look, Map<number, boolean>>` 或等价），稠密预分配入负面清单。

（已核不立案的相邻面：`Object.keys(value)` 对 10⁸ 键对象物化键数组——O(键数) 一次性、与逐键计费同阶，属调用方已为快照本体支付过的同阶成本，R2-3 的防御论证覆盖；封闭对象 present() 检查的 hasOwn——schema 侧受字段数约束、不可按节点放大。）

### 2.2 R3-2（MEDIUM）v1 契约推导两处未取最坏口径——「合计保守界」不保守

**(a) 联合重入乘数。** §5.7-3 乘法链的第三层「节点访问乘数 = 每节点全程 ≤ ~10 单位（validateValue 进入 1 + …）」——「进入 1」对含联合的 schema 为假。§5.2 段 2 对**全部**成员跑 countIssues（R2 删短路的正确决定，代价如实）+ 段 3 对 winner 跑 dive：同一快照子树被 Π(Nᵢ+1) 次计费进入（每层：Nᵢ 次 countIssues + 1 次 dive）。成员子树全相异时（不同别名 → 不同节点对象），countMemo 键互不碰撞——这正是 §5.7 第 2 层自己承认的「非共享深乘积类被构造性兜底」：**运行时安全**（loud fail-closed，~1s，不挂死不误判——我方确认第 2 层兜底成立），但第 3 层的契约表把「快照节点访问 ≤ 10⁶ ≈ 10⁷」当作无联合假设的通用行——契约三行全合规的调用可仍触顶。契约是 R2-2 修订的核心交付物（「显式规模契约」），其推导必须把该乘数列入乘法链（或把节点行重定义为计费进入数——两种修法任一均可，均是一行的事）。

**(b) preview 最坏单位。** 节点行按 ~10 单位/节点计，但其自注「preview 48 仅枚举位」意味着枚举位最坏 51 单位/节点。§4 消息表把 preview 内嵌在 issue 消息里、`emit(message, path)` 的 message 在调用前构造——**计数态（>100 条后）照常构造消息、照常跑 48 单位 preview**（计费表确实收了这 48——账是对的，只是契约行没按它排合计）。10⁶ 个全错的枚举元素：5.1×10⁷ 单位；与 T1 行 1.35×10⁸、T2 行 5×10⁷ 同排满 → 2.36×10⁸ > 2×10⁸。最省事的修法是把消息构造（含 preview）门控在物化态（收集器满 100 后只数数不造消息）——同时让计数态的字符串垃圾归零，一举两得；或者 WORK_LIMIT 上调至 2.5×10⁸ 并按 51 重排。无论哪种，修后「合计保守界」必须真的等于各行上限之和。

两处都不影响旗舰场景（3_000 AssetId：单层联合 ×4 已含在 50/键内、枚举错位不占主导——1.7×10⁷ = 8.5% 复算成立），也不产生错误校验结果——破坏的只是契约作为「契约内调用必在预算内」这一**冻结承诺**的推导完整性。这正是 R2-2 的病灶（乘法/口径没做全）在重写后的两个残留，故立 MEDIUM 而非 LOW。

### 2.3 R3-3（LOW）对账句失实

见清单。机制四行计费（键/元素/emit·overflow/preview）与字段名索引、preview 有界化本身全部成立（R2-3 核验通过）；失实的只是「10⁸ 键 → 10⁸ 单位 > WORK_LIMIT」这一句示例——它同时漏计自家记账行（1/键）与沿用旧上限直觉。SA4 若按此句设计验证测试（10⁸ 键断言 loud）会得到完成而非耗尽。一句话修正。

### 2.4 R3-4（LOW）T2 包络边界 ~0.7% 偏差

见清单。纯声明精度：严格蕴含式应为 P(len+1)(len+2) ≤ 512len²+1024len+16384（全 len 域仅 P ≲ 512·len²/(len+1)(len+2) 时成立，线性项/截距只在 len ≤ 30 给出补偿）；窗口 (30, ~86) 内超界 ≤0.7%，被设计自陈的 3~10× 实际余量完全吸收。不构成行为风险，修不修不影响放行判断，但「定理界 ≤ 预算」作为列名是精确断言，边界要么修系数要么修脚注。

## 8. 结论

R3 对 R2 六项发现的处置是完整且诚实的：两 HIGH（定理分列、组合包络）的核心交付物经我方独立复算与 14 条同版本实测复核成立，两 MEDIUM（计费补行、转义统一）与两 LOW（混合引擎否决、`|` 行）全部落地，R2 的「用设计自家数字证伪」病灶均有自认复盘。本轮 reject 的依据集中于 R3 **新引入**的两个条款：
