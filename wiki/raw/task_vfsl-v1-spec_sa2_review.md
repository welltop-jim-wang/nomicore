## 2. 攻击点详述（触发条件 / 影响 / 修订要求）

### F1（CRITICAL）默认物化表的联合行与 §0.3 推演自相矛盾

- **触发条件**：任何读者按 §3 表格字面解释 `Record<AssetId, AssetEntity>`——`AssetEntity` 是「联合」且处于容器（Record 值位）内，命中「容器内的原始类型 / 字面量 / 联合 → 原生叶子值」行。
- **影响**：该读法下每个资产实体是纯 JSON 叶子，而其成员内嵌 `audit: Audit`（`YMap` 物化）——同步 Y 类型住进非同步 JSON 值，正是 §0.3 推演 1 用**同一个矛盾**反推出「裸对象必须默认物化为 Y.Map」的。设计最重要的推演与它自己的结论表冲突。对照 YLeaf 形状约束行写的是「原始类型 / 字面量 / **其**联合」——一个「其」字之差暴露了遗漏。附带三个同族空洞：混合联合（`{a: string} | number`）物化未定义；`YMap<对象形联合>`（D3 显式允许）的键空间语义未定义；`YArray<{…} | string>`（实参任意）元素级物化未定义。issue #5/#6 在这些位置全部要做无规格依据的静默决定——恰是 D3 自己声称要预防的。
- **修订要求**：① 表行改为「原始类型 / 字面量及其联合 → 原生叶子值」；② 新增一行「含对象 / 数组成员的联合 → 按命中成员的形状物化（多态值形状），成员各自适用默认/标记规则」；③ 混合联合（标量与容器成员并存）给出 v1 立场——建议拒绝（新错误码或明确归入 E100，写死）；④ `YMap<对象形联合>` 键空间一句话成文（建议：各成员键集之并的封闭）。

### F2（HIGH）18 个错误码没有传递通道

- **触发条件**：issue #5 实现 parser 时要在测试或调用方呈现错误码。
- **影响**：PRD #3 Implementation Decisions 冻结「唯一公共测试接缝：`parseVfsl(text)` → …`{ ok: false, issues: [{ message, line, column }] }`」——无 code 字段；D9 又声明规格不冻结 issues 字段形状（PRD 所有权）。两头一夹：码既进不了 PRD 接缝（进 = 违反接缝冻结），又没有第二通道。issue #4 的目标陈述是「可直接作为实现依据」，而它的核心交付物（18 码结构化错误语义，AC #3）在运行时通道上是断头的——要么码变装饰，要么 issue #5 私改接缝（无规格依据的契约变更，SA4 会卡）。
- **修订要求**：成文一条通道契约，最小侵入方案：**「错误码以 `message` 的冻结前缀格式呈现（`VFSL-E<nnn>: <人类可读消息>`）」**——PRD 接缝零改动、测试可断言、实现间可比。若 SA1 更倾向扩展 issues 字段，则必须显式声明「该扩展属 issue #5 的接缝决策点，须回 PRD 走变更流程」并把此边界写进 §4.3 下游契约面声明。二选一，不可留白。

### F3（HIGH）禁止构造检测机制未定义，四码形式不可达

- **触发条件**：按 §2 文法逐字实现 parser 并输入六项禁止样例。
- **影响**：`Module = { TypeAlias }`、`TypeAlias = "type", Ident, "=", …`——`interface A {}` 不以 `type` 开头 → E100；`type Box<T>` 在 Ident 后遇 `<` 非 `=` → E100；`A extends B` 在 TypeRef 后遇 `extends` → E100；`{ [K in …] }` 字段位遇 `[` → E100。**E102~E105 在冻结文法下形式上不可达**，错误码总表与文法冲突；错误锚点（如 E102 锚「`<` 起点」）暗示了特征检测，但检测顺序无条款。同族问题：`YLEaf<string>` 按 §6 应 E301，文法下却是「TypeRef 后遇 `<`」的 E100；`any` 不在保留名集合 → `type any = string;` 通过 E303，但 `type T = any;` 恒 E101——一个合法声明永不可用，规格自我矛盾。
- **修订要求**：§4 增补规范性「错误判定顺序」：tokenizer/parser 在落入 E100 前，先按禁止构造特征映射专属码——模块层前导 `interface` → E105；别名名后随 `<` → E102；类型位置 `extends` → E103；字段名位置 `[` → E104；类型位置 `any` → E101；`<` 前的标识符非 Record/六标记且为未声明名或标记变体 → E301（锚引用记号），已声明别名 → E100（锚 `<`）。同时把 `any`、`extends`、`interface` 加入保留名集合（或显式注明它们作为别名名的处理），消除 `type any = …` 矛盾。

### F4（HIGH）Comment 产生式悬空，「完全可推导」声明为假

- **触发条件**：以严格文法视角检查附录 fixture 的可推导性（AC #1 的字面要求）。
- **影响**：文法中 `Comment` 及三个子产生式没有任何引用点——`Module`、`FieldList` 均不容注释；词法元符号注记只豁免 char/digit/letter/eol。若注释是语法成分，fixture 的 5 处注释（4 处别名级 + 1 处属性级）使文本**不可推导**，§4.2 的「该文本按 §2 文法完全可推导」与 D14 的「可推导性实证」不成立，AC #1「EBNF 能推出 fixture 的每个构造」字面失败。若是词法 trivia，规格又没写「注释与空白允许出现在任意记号边界」——issue #5 连 `type/*c*/A=string;` 合法与否都无从回答。
- **修订要求**：语法注记增补第 9 条（或并入现有注记）：「空白与注释是词法级 trivia，可出现于任意记号边界，不参与语法推导；`Comment` 系列生产式仅规范注释自身的词法形状，作为 E203 判定与 §5 原文捕获的依据」。同步把 §4.2 措辞改为「除词法 trivia 外完全可推导」。

### F5~F9（MEDIUM）摘要

均见清单表「建议」列；共性是：每一处都会迫使 issue #5/#9 做静默决定，与 D3「预防 parser 拿到规格仍要做大量静默决定」的设计目标直接冲突。修订均为一两句话条款，不触及章节结构。

- **N1**：触发——issue #5 负例测试必然覆盖的输入：`type T = YMap;`、`type T = string<number>;`、`type type = string;`、`type T = Pattern;`。影响——E301 行把「未声明」定义为「模块内无该名 TypeAlias 声明」，保留名永不可能有声明 → 字面读法下这族输入全落 E301；而形状约束表明写「裸 Pattern → E100」，裸 `YMap` 却无任何条款——同族构造两套判决。判定顺序第 6 条只覆盖「`<` 前的标识符」：裸引用（无 `<`）与 `string<`（PrimitiveType 终元还是 Ident？）均落在条款外。两种 tokenizer 设计（keyword 记号 vs 统一 Ident+后置查表）都合法，产出两套错误码，测试断言分裂——与 D16 要消灭的「四个实现四种报法」同性质。修订——判定顺序增补第 7 条：「保留名记号出现在其对应产生式不适用的位置（裸标记引用、内置名后随 `<`、声明名位 keyword）→ 统一 E100（锚该记号）；E301 仅适用于非保留名的标识符记号」，形状表「裸 Pattern → E100」保留为该族实例；`type type = …` 在该条或 E303 行内给唯一答案。

- **N3**：触发——`type A = B; type C = (`（line 1 语义 E301 在前、line 2 语法 E100 在后）。影响——基线 §4「parser 报告文本位置最前的一处错误并立即失败」按字面要求报 line 1，但 E301 判定前提是模块全量解析（判定顺序末段自设），解析已在 line 2 失败——字面规则不可实现；分相位实现报 E100、收集后取最小实现（若有）报 E301。修订——改为：「词法/语法错误即时失败并即报；仅当全量解析成功才进入 E3xx 语义相位，语义相位内取文本位置最前」。判定顺序的「多特征命中取位置最前」不受影响（同记号内）。
- **N4**：触发——多行 `/**\n * x\n */`（§5 原文捕获「含缩进」隐含其存在）；文件末行 `// c` 且无换行结尾。影响——`char` 元符号未定义且按产生式语义不同（字符串排除行终止、注释包含行终止）；严格按「排除 eol」实现注释的 parser 会把多行文档注释误报 E203；行注释的 eol 终结在 EOF 无换行时无条款。修订——词法注记补一句（见清单表「建议」列）。
- **N5**：触发——任何读者按澄清句独立解义。影响——见清单表；上下文已由「并集（封闭）」锚定意图，故仅 LOW。修订——一句措辞替换。
