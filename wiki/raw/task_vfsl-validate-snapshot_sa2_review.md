## 2. 逐项详述

### 2.1 #1（CRITICAL）联合扫描指数爆炸——ADR 0003 §4 的消费者预算缺失

**攻击构造**（探针 P6 实测合法）：

```
type U0 = string;  type V0 = number;
type U1 = U0 | V0;  type V1 = U0 | V0;
…（U_k = U_{k-1} | V_{k-1}; V_k = U_{k-1} | V_{k-1}）
type ROOT = { m: U40 };
```

全标量联合，E309 折叠为 scalar，每别名语法深度 2——`MAX_TYPE_NESTING=100` 完全不设防。值树：`values['U_k'] = union{[ref U_{k-1}, ref V_{k-1}]}`（enum 折叠只认全字面量，ref 成员不折叠）。

**触发条件**：对 `{m:{}}`（或任何不匹配值）调用 `validateSnapshot`。§5.2 段 2 `distances = members.map(countIssues)` 对每个成员做完整校验；`countIssues(U_k)` → `countIssues(U_{k-1}) + countIssues(V_{k-1})`，而 `U_{k-1}` 会被 U_k 与 V_k **各调用一次**——§3.1 的 memo 只覆盖 ref→目标的**解析**，不覆盖 (节点, 值) 的**校验结果**。递推 T(k)=2·T(k−1)。

**影响**：k=40（约 82 行 VFSL）→ 2^40 ≈ 10^12 次成员扫描，同步挂死数小时；k=50 → 不可行时长。无任何预算拦截——§6 的步数预算只存在于 Pattern 引擎内部。这正是 §6.1 自己否决「静态风险分析」时的判词：「漏报即挂死，防护承诺破产」。**ADR 0003 §4 明文：「菱形引用链的全展开爆炸（2^N）只在枚举型消费时发生——枚举预算是消费者策略，不进引擎契约」——validateSnapshot 就是该消费者，本设计没有兑现这份委托。**

**修订要求**（二选一或组合，须写入设计并论证）：
1. **每调用全局工作预算**：成员扫描计数器（或全局指令步数），超限 loud issue（镜像 §6.5 的「预算耗尽」语义：fail-closed、可区分消息），预算值与标定依据冻结；
2. **(resolved node, value) 记忆化**：以解析后节点对象 + 值对象引用为键 memo `countIssues`/`dive` 结果，菱形坍缩为线性——但这只治菱形，仍需预算兜底对抗非共享的深乘积（嵌套联合 × 多成员）。
推荐组合：记忆化（消除 ADR 明示的菱形类）+ 全局预算（构造性兜底一切）。

### 2.2 #2（CRITICAL）SA6 红灯 `YPlainArray<{…}[]>` 不可满足，§11 对账失实

**事实链**：
- 红灯测试（validate-snapshot.test.ts:422-434）：文本 `YPlainArray<{ name: string; count: number }[]>`，断言 `{items:[{name:'a',count:1}]}` → `ok:true`，且 `{items:[{name:'a',count:'x'}]}` 存在长度 3、以 `count` 结尾的 path。
- 探针 P1 实测派生树 = `array(array(object))`（#20 设计 §6 冻结映射的直接产物，evaluate.ts:302）。
- 忠实解释值树（本设计 §1.2 的核心决策）：`items[0] = {…}` 对内层 `array` 节点报「类型不匹配：期望数组，实际 object」→ `ok:false`、path `['items',0]` 长 2——**两条断言（ok:true / 长 3 path）均永不满足**。

**影响**：SA3 按设计实现则该测试永红；更危险的是诱使 SA3 用「YPlainArray 实参拍平」「array 节点宽容」等私改映射兜底——那会静默破坏 #20 已冻结的派生语义（双重数组本身就是 `YPlainArray<T[]>` 的正确含义：元素是 `T[]`）。设计 §11 该行写「嵌套封闭对象 `['items',0,'count']` 长 3 ✓」——SA1 未对该测试做派生树核对，对账失实。同 describe 第二条（`YPlainArray<string | {a:number}>`）单层数组，无此问题。

**修订要求**：设计新增显式处置节：判定该红灯为 SA6 测试文本缺陷（`[…]` 应写 `YPlainArray<{ name: string; count: number }>`，断言逻辑不动），依 ALLOW LIST「测试基础设施级修正且须在 PR 说明」授权修正；同时建议补一条 `YPlainArray<{…}[]>` × `[[{…}]]` 的正例，把双重数组语义锁死在测试面，堵死 SA3 的拍平冲动。

### 2.3 #3（HIGH）转义子集缺 `\-`——fixture 自身的 Pattern 会编译失败

§6.2 字面量转义清单：`\\ \. \* \+ \? \( \) \[ \] \{ \} \| \^ \$ \/ \n \r \t \f \v \0`、`\xHH`、`\uHHHH`——**无 `\-`**；字符类行只写「类内转义」四个字，未枚举。而探针 P2 实测 fixture AssetId 解码正则为 `^[A-Za-z0-9_\-]{1,64}$`——`\-` 在类内。SA3 若按清单字面实现：`\-` 落入「子集外构造」或语法非法 → §6.5 loud issue → **fixture 的 Record 键 Pattern 全部编译失败**——`assets` 下每个键都报错，合法快照 `ok:false`，fixture 相关约 15 条测试连环红（含合法快照 → ok:true 这条）。

**修订要求**：§6.2 字符类行枚举类内转义全集：至少 `\\` `\]` `\^` `\-` + 类内 `\d \D \s \S \w \W` + `\n \r \t \f \v \0` `\xHH` `\uHHHH`；并定稿**类外 IdentityEscape 立场**（Annex B 宽松：非特殊含义的 `\<字母>` 按字面量，如 `\q` → `q`，与 ECMAScript 无标志行为一致——否则大量 JS 合法模式被 loud 拒，子集偏离面不必要地扩大）。子集边界是 §14 自认的「SA2 主场」冻结项：边界可以窄，但必须**枚举完备、无 fixture 自伤**。

### 2.4 #4（HIGH）匹配器对合法输入的健全性缺口（空循环守卫 + 记忆化）

**(a) 空宽度循环无守卫**。§6.3 字节码的 `*`/`+` 是 `Split` 循环，无 progress 检查。子集内模式 `(a?)*b`（`a?` 可空匹配）：对输入 `'b'`（**真值匹配**，ECMAScript `(a?)*b`.test('b') === true），执行从 pos 0 无限循环压入回溯点（每次迭代 a? 空匹配、pos 不动）——直到步数预算耗尽 → §6.5「无法判定」issue → **合法快照被误拒**。`(a*)*b`、`((?:a|b)?)*x` 同类。红灯 `(a+)+$` 不触发此坑（`a+` 每迭代消费 ≥1 字符），测试无覆盖。
**修订**：循环体重入时 pos 自上次迭代未推进 → 强制走出口分支（标准 empty-width check），语义与 ECMAScript 一致。

**(b) 无 (pc,pos) 记忆化 → 小输入误拒**。`(a+)+b`（§6.6 自己认证「嵌套量词在子集内」）× 输入 `'a'*20 + 'c' + 'a'*5 + 'b'`（27 字符，**真值匹配**：start 21 处 `a+`→`b` 命中）：start 0 的 (a+)+ 对 20 个 a 做 2^19 量级分区探索 ≫ 预算 4096（len=27 → `max(4096, 64×27+1024)=4096`）→ 预算在 start 0 耗尽 → 误拒合法值。§6.4 标定表只有「锚定线性模式」与「病态炸弹」两类；**「非锚定 × 中庸模式 × 结构化不匹配前缀」这一类目缺位**，而它恰是预算公式给出 false-reject 的地带。
**修订**：执行器增加每起点 (pc,pos) 已访集（使任意子集内模式的单起点成本 ≤ 程序规模 × 输入长），或等价 NFA 化模拟；随后**重标定 §6.4**：论证「预算耗尽 ⟹ 真病态（合法输入在预算内多项式完成）」。注意重标定后须重新对账 ReDoS 红灯：`(a+)+$` × `'a'*32+'!'` 在记忆化下多项式完成并正确得出「不匹配」→ `ok:false` 断言**仍绿**（红灯只锚 ok:false 与不挂死，不锚「预算耗尽」消息）——修复与验收兼容。

### 2.5 #5（MEDIUM）O6 措辞与惰性编译矛盾

O6（§1.3）与 §6.5 的读法是「非法正则 → 一律 ok:false + loud issue」。但设计的编译时点是 `validateValue` 到达 pattern 节点（含 §4.1 的 Record keyPattern 逐键判定）——**惰性**。于是：`type T = string & Pattern<"[">` 用于 optional 字段且快照缺席 → 永不编译 → `ok:true`；空 Record（无键）的 keyPattern → `ok:true`；空数组元素 pattern → 同。spec §9.1 只说「暴露时点属语义层（validateSnapshot）」，两读皆可自圆，但设计**内部**承诺（「不静默」）与算法**实际**行为不一致。急切编译不可取：pattern 节点经别名共享，issue 的 path 无唯一定位（fixture 的 AssetId 模式同时是 Record keyPattern 的来源）。
**修订**：定稿「**使用时暴露**」语义，改写 O6 行与 §6.5 引言（「到达即 loud」）；红灯思路见 §5。

### 2.6 #6（MEDIUM）回溯栈内存无界，OOM 绕过 E100

§6.3：压入 `(pc, pos, captures 副本)`。步数预算封顶 2M 条指令，但每条 Split 压栈伴随 O(nSlots) 的捕获拷贝且**计 1 步**。构造 `(?:(a)|(b)|(c)…50 组)*` 类模式（程序 ≤10k 指令内）× 病态输入：2M 步 ≈ 2M 栈条目 × 100 slot ≈ GB 级堆 → V8 OOM **不是异常**，顶层 catch 收编不了，进程直接崩——比挂死更糟（连 E100 都没有）。
**修订**：回溯点只存 `(pc,pos)`，捕获用 undo-log（Save 记录旧值，回溯按日志回滚）或 copy-on-write；或将 nSlots 拷贝计为 nSlots 步纳入预算。给出内存上界论证（应为 O(活跃捕获 + 栈深 × O(1))）。

### 2.7 #7（MEDIUM）XML 顶层文本禁令与 Yjs 投影冲突

§7「顶层非空白文本 → false（片段是元素序列）」——论断不实：`Y.XmlFragment` 的子节点可含顶层 `Y.XmlText`，其 `toJSON()` 投影是**顶层纯文本**（如 body 为 `'hello world'`）或**文本与元素混合**（`'hi <b>b</b>'`）。这些是合法 Yjs 投影、也是「良构 XML 片段」（外部实体语义允许多根与顶层文本——设计自己已采纳多根森林，唯独禁了文本，半途而废）。按现设计，合法快照被误拒。红灯不覆盖此界（fixture 只用 `<p>…</p>`），SA1 有修正自由度。
**修订**：允许顶层文本（与片段语义一致化：多根 + 顶层文本均合法，仅要求标签栈平衡与良构结构）；或给出「Yjs 投影不可能顶层文本」的权威依据（给不出就该放宽）。另：属性值引号内 `'>'`（XML 合法）须作为原子单元扫描，否则 `<p title="a>b">` 误判——写明。

### 2.8 #8（MEDIUM）§11 与 §5.2 的段落归属矛盾

§11「结构校验」行：「联合命中成员内未知键 …✓（**段 2 接受 image 后**下钻，封闭语义照常）」。§5.2 段 2 的接受定义是「零 issue → 接受（**零输出**）」；带未知键的 img1 对 image 成员 countIssues=1，段 2 **不**接受——实际路径是段 0 命中但 issue>0 → 段 1 候选过滤 → 段 3 dive。两处输出恰好相同（dive 都发那条未知键 issue），测试不 discriminating，但「唯一权威伪代码」附录第 1 条明令以 §5.2 为准——§11 的反向叙述是现成的走样素材。**修订**：改 §11 措辞为「段 3 候选分支 dive」。

## 4. 错误处理链路审查（SKILL 2026-05-07 立法）

纯函数库，无 UI/按钮/异步任务——按同构判据审查：

- **静默失败**：一切失败经 `ValidateResult` 返回值传递；意外异常顶层 catch → E100 issue（§2.2/§10）✓。例外计入清单：#6（OOM 绕过 catch）、#4（合法输入被误拒是「错误输出」而非静默，但属正确性缺口）、#5（未使用位 Pattern 的 ok:true 是否算静默，待定稿措辞）。
- **状态闭环**：收集器两态（物化/计数）+ 末尾截断标记，溢出有精确计数闭环 ✓（§8 论证自洽，红灯 150→101 对账核符）。
- **降级路径**：无外部依赖，不适用 ✓。

**结论：本节通过（#5 措辞修正后闭环）。**

## 7. 结论

设计的架构主线（值树解释器 + 三段联合算法 + 受限回溯匹配器 + 两态收集器）方向正确，§5/§8 的红灯对账在 fixture 面上经真实派生树验证成立；但**资源完备性与对账真实性各有一处 CRITICAL 破洞**：

1. #1 联合扫描无消费侧预算——与 ADR 0003 §4 的明文委托直接违约，且与 §6.1 自身的防护完备性论证自相矛盾；
2. #2 SA6 首条 YPlainArray 红灯在冻结映射下不可满足，设计 §11 对账失实——不定稿处置则 SA3 无诚实转绿路径。

另有两处 HIGH（转义子集自伤 fixture、匹配器对合法输入不健全）决定 SA3 的实现正确性，要求随修订一并定稿。**Verdict: reject**——请 SA1 按 §2 各项修订要求出 R2，SA2 复审通过后再放行 SA3。
