# [Bug] ws-replication 命名空间生命周期跨连接代际竞态（hub 迟到续体复活/泄漏、peer cleanup 入口捕获错代、CLOSE_OK 静默错配、GOAWAY 迟静默）

**Status**: analyzed | **Date**: 2026-08-30
**Severity**: high
**Type**: new-feature-defect（功能随 08da15b #162 引入、ef19bae #165 加固成型；非既有功能回归）
**Layer**: backend（`packages/ws-replication`，hub-connection/hub-namespace + peer-connection/peer-namespace 双侧）

## Symptoms

PR #165 合入 `docs/phase-5-websocket-replication` 后，review（issue #161 反馈）发现命名空间生命周期操作可跨「连接代际」（connection generation，非 replication epoch）串扰。用户可观察到的故障面：

1. Hub 连接静默（socket 断开/`connectionFatal`/`close()`）时，在途 `authorize`/`registry.open`/`openReplicationSession` 续体不中止：向已静默连接补发迟到 `OPEN_OK`/`BOOTSTRAP_SNAPSHOT`，通道状态从 `closing` 倒退回 `bootstrapping`（旧命名空间复活）；若续体在连接收口完成后才恢复，新拿到的 lease/session 被原地丢弃——Registry lease 永久持有、session 槽位泄漏（idle 永不到达）。
2. Peer 侧排队 cleanup（`cleanupTail`/close 续体）在入口才捕获 session/lease/unsubscribe——旧代 cleanup 进入时若新连接已重建订阅，会把新代 listener 摘除、teardown 新代 round/channel/watchdog（新连接上行静默死亡）。
3. `removeTarget()` 在 `CLOSE_NAMESPACE` 未上线（sendControl 静默返回 0）时仍等待 `CLOSE_OK`，挂满 `closeTimeoutMs`；伪造/错配 `CLOSE_OK` 被静默忽略而非按 ACK/协议违例显式收口。
4. GOAWAY `SERVER_RESTARTING` 只在 drain deadline 定时器回调里静默订阅——GOAWAY 收到至 deadline 窗口内控制器仍可开新 sync round、继续收发数据，违反协议 §6.3「收到 GOAWAY 后停止 OPEN，不开始新 sync round」。
5. `LifecycleQueue` 类已删除（零引用死抽象），hub 用内联 `closeQueue` promise 链、peer 用 `Memoized`+`cleanupTail`+settle gate 三套并存，与 §16「单一生命周期队列」不符。

## Reproduction

纯静态可推导（测试 harness 可注入时序复现，无需运行时诊断日志）：

- **H1/H2（hub 迟到 open 续体）**：peer 发 `OPEN_NAMESPACE` → hub `onOpenNamespace` 建通道并 `startOpen`（hub-connection.ts:352-354）→ 在 `host.authorize` / `registry.open` / `lease.openReplicationSession` 三个 await 挂起期间断开 socket → `onTransportClosed` → `cleanupAll` → `quiesceConnection()`（置 `closing`）→ `onConnectionClosed()`（closeQueue 链收口）。续体恢复后 `isTerminal()` 为 false（`closing` 非终态）→ 继续赋 lease/session、发 `OPEN_OK`+`BOOTSTRAP_SNAPSHOT`。
- **P2/P3（peer cleanup 错代）**：gen1 live → cleanup A 进入 `closeSessionAndRelease` 后卡在 `session1.close()` 屏障（在途 apply 排空慢）→ 断线（cleanup B 排入 `cleanupTail` 等待 A）→ 重连 gen2 → `onConnectionReady` → `startOpen` → session2+listener2 建立 → A 结算、B 进入：入口捕获到的已是 session2/lease2/listener2 → 摘 listener2、teardown gen2 round/channel/watchdog、close session2、release lease2。
- **P4（CLOSE 未上线仍等待）**：connState ≠ ready（或 sender 配额耗尽等）时调用 `removeTarget()`（state 为 live 族）→ `sendControl` 返回 0（peer-connection.ts:461-469）→ `closeSequence = 0` → `onCloseOk` 永不匹配 → 挂满 `closeTimeoutMs`。
- **P7（GOAWAY 迟静默）**：peer live 期注入 `GOAWAY{reasonCode:'SERVER_RESTARTING', drainTimeoutMs:N}` → 控制器状态不变，`needs-resync` 恢复路径仍可 `startRound`；N ms 后定时器回调才 `quiesceControllers()`。

## Investigation

阅读链（共 8 文件，≤10 上限内）：`wiki/raw/task_issue-171.md` → `task_issue-171_relevant_decisions.md`（ADR-0010/#161 修订节「代际安全脱离」「同步静默订阅先于异步 drain」为直接前置决议）→ `packages/ws-replication/src/hub-namespace.ts`（893 行全读）→ `peer-namespace.ts`（1043 行全读）→ `lifecycle-queue.ts` → `hub-connection.ts` L150-429（cleanupAll/quiesce/dispatch）→ `peer-connection.ts` L360-659（GOAWAY/onClose/enterBlocked/onTemporaryFailure/requestRebuild）→ `docs/protocols/instance-replication-v1.md` §§6.3/7/12/13/15.1/16/18。

分析路径：以 Scope 七项为索引逐项做时序推演——对每个 await 点列出「挂起窗口内可发生的连接事件」（quiesceConnection/onConnectionClosed/onConnectionLost/重连+onConnectionReady/removeTarget），核对恢复点的守卫条件（`isTerminal()`/`isConnectionDead()`/epoch 比对/identity 捕获）是否覆盖该窗口。关键不对称：#165/#136 已给 peer 的 open/apply 续体接上 `connectionEpoch` 判别（peer-namespace.ts:191/224/294/321/386/405/785/810），但 **hub 侧完全没有等价机制**（`HubChannelHost` 无 epoch 面），且 **peer 的 close/cleanup 续体不在 epoch 防护面内**（入口捕获语义）。git 考古确认代码成型于 ef19bae（#165，2026-08-29）与 08da15b（#162），#165 提交说明 G4 自述「CLOSE_OK 错配不完成 close——closeTimeout 兜底」「GOAWAY 重构」即本次被推翻的两处旧决策。

## Root Cause

按 Scope 七项逐一定位（文件:行号以 worktree 当前 HEAD ef19bae 为准）：

**RC1（Scope 1，hub 迟到续体不把 quiesce 当中止）** — `hub-namespace.ts`
- `startOpen` 全部恢复点守卫是 `this.isTerminal()`（L239、L254、L278、L316），而 `quiesceConnection()`（L574-581）只置 `closing`——非终态。续体继续执行 L266 `this.lease = opened.lease`、L326-330 赋 session+订阅、L333 `flushOpenWaitersOk()` 补发 `OPEN_OK`（L355-362）、`startBootstrap` L389 `setState('bootstrapping')`（从 `closing` **倒退**，复活）+ L426 补发 `BOOTSTRAP_SNAPSHOT`。
- **泄漏变体**：若续体在 `onConnectionClosed()` 的 closeQueue 链已完成后才恢复（state 已 `closed`），L239/254/316 命中 `finishOpenSilently()`（L377-381）——但该路径只回收 `this.lease`/`this.lease` 字段；`registry.open` 已交付、尚未赋给字段的 `opened.lease`（L249-266 之间）与 `openReplicationSession` 已交付、尚未赋值的 `sessionResult.session`（L308-326 之间）被原地丢弃，**永不 release/close** → lease 持有 + session 槽位泄漏（ADR-0009「释放恰一次」破坏）。
- 结构性根因：hub 的 open 异步流程完全**不挂接** `closeQueue` 生命周期链（L93/L542），open 续体与 cleanup 链零串行化；hub 侧无 connectionEpoch/代际概念。

**RC2（Scope 2，peer cleanup 入口捕获错代）** — `peer-namespace.ts`
- `cleanupResources()`（L988-995）把 `closeSessionAndRelease` 排入 `cleanupTail`，但 session/lease/unsubscribe 在**进入执行时**才捕获（L958-960）；B-2d 守卫 `this.session === session && this.lease === lease`（L965）比较的是入口身份——旧代 cleanup 若在新代订阅后才进入（排在 `cleanupTail` 链后/`drainPendingApplies` 后），捕获到的就是**新代**资源，守卫恒通过 → 摘新 listener、teardown 新 round/channel/watchdog、close 新 session、release 新 lease。`onCloseRequest` IIFE（L499-509）与 `ensureCloseMemo` body（L595-599）先 `drainPendingApplies` 再进 `closeSessionAndRelease`，同样的后置捕获窗口，且 L502-506 的 `CLOSE_OK`（旧 ackedSequence）可能落到重连后的新连接。
- 附带缺陷：`closeSessionAndRelease` 入口 L961 无条件 `this.quiesceSync()`（L949-955）退订的是**当前** `this.unsubscribe`（可能是新代 listener），与 L970-975 R4-2 注释宣称的「仅退订本 cleanup 捕获的句柄」自相矛盾——L973 的二次判等在 quiesceSync 已清空字段后结构性失效。
- 缺失件：cleanup 在**排队时**捕获 connectionEpoch/session/lease/unsubscribe 所有权。

**RC3（Scope 3，onConnectionLost 分支清理不全）** — `peer-namespace.ts` L621-637
- `closing` 分支（L624-628）：settle closeMemo 但不 `clearTimer('close')`，也不清 open/bootstrap/reconcile 残留 timer（`removeTarget` 从 `bootstrapping`/`reconciling` 进入 `closing` 时这些 timer 仍武装——L553-565 只 arm 'close'），且自身不触发 cleanup（依赖 close 发起续体，该续体又是 RC2 的错代载体）。
- 活跃分支（L634-636）：不断 open/bootstrap/reconcile timer——断线停留 `disconnected` 期间旧 open/bootstrap timer 触发 → `onTimerFired`（L1029-1042）非 close 路径直接 `finalize('failed')`：从 `disconnected` 置 `failed`（语义污染：连接丢失被记为 ns 终局失败）并再入 cleanup，与重连 open 竞态。
- `failed` 分支（L629-632）无任何动作；watchdog/round/channel/ACK-timer 的 teardown 全部推迟到异步 `closeSessionAndRelease`，断线同步段只摘 listener（`quiesceSync`）。

**RC4（Scope 4/AC3，CLOSE 未上线仍等待）** — `peer-namespace.ts` L553-565
- `this.closeSequence = this.sendChecked({kind:'CLOSE_NAMESPACE',...})` 不检查返回序。`peer-connection.sendControl` 在 `connStateValue !== 'ready'` 或 outbound/sender 未就绪时**静默返回 0**（peer-connection.ts:461-469）；`peer-namespace.sendChecked`（L879-891）只对 throw 分支有反应，0 直接透传。`closeSequence=0` 永无匹配 `CLOSE_OK`（wire 序列从 1 起）→ `removeTarget` 挂满 `closeTimeoutMs`。

**RC5（Scope 5/AC4，错配 CLOSE_OK 静默）** — `peer-namespace.ts` L512-520
- `onCloseOk` 仅在 `state==='closing' && ackedSequence===closeSequence` 时收口，错配/迟到/伪造帧**静默忽略**。对照同库权威 ACK 关联策略：hub `onBootstrapAck` 错配 → `connectionFatal('ACK_STATE_VIOLATION', 1002)`（hub-namespace.ts:450-456）；`onUpdateAck` → channel.onAck 'violation' → 同款 fatal。CLOSE_OK 错配既不显式报错也不加速收口（只能耗尽 closeTimeout）。#165 G4 提交说明自述此为旧决策「错配不完成 close——closeTimeout 兜底」，issue #171 推翻。

**RC6（Scope 6/AC5，GOAWAY 迟静默）** — `peer-connection.ts` L398-412
- `SERVER_RESTARTING` 分支把 `quiesceControllers()`（摘订阅+投影 disconnected+cleanup）整体放进 `drainTimeoutMs` 定时器回调；GOAWAY 收到至 deadline 窗口内控制器状态不变（live/needs-resync），`maybeStartRecovery`（peer-namespace.ts:711-718）/`declareLocalResync` 仍可开新 sync round、`sendFacet.pullAndSendOne` 继续出数据帧——违反 §6.3「收到 GOAWAY 后停止 OPEN，不开始新 sync round（同步）」与 #161 修订节「GOAWAY…同步静默订阅先于异步 drain」。deadline 应只管 transport close。
- `goawayActive`/`isGoawayDraining` seam（peer-connection.ts:94 → peer-namespace.ts:51-52 接口声明）**零消费**——控制器结构性看不到 drain 窗口（死 seam）。
- `SERVER_SHUTTING_DOWN`/`REAUTH_REQUIRED` 走 `enterBlocked()`（L595-613）同步 `onConnectionFatal` 各控制器，该路径基本符合同步静默要求。

**RC7（Scope 7，生命周期权威分裂/死抽象）** — `lifecycle-queue.ts` L7-9 自述：`LifecycleQueue` 类已删除（零引用），hub 用内联 `closeQueue` promise 链（hub-namespace.ts:93/L542）、peer 用 `Memoized`（lifecycle-queue.ts:13-24）+ `cleanupTail`（L88）+ `closeSettleResolve` gate（L91-93）三套并存——§16 明文「Target controller 用**单一**生命周期队列串行化 removeTarget、socket close、session close 与 Lease release」。RC1 的「hub open 不上链」与 RC2 的「peer 三机制交错」都是该分裂的直接后果。`isGoawayDraining` 为另一处死抽象（RC6）。

**Fix direction**（供 SA1 设计参考，不展开实现）：
1. 引入统一的代际令牌（hub 侧补 connection epoch/generation 面；peer 复用 `connectionEpoch`），所有 open/authorize/session/cleanup 续体在**发起时**捕获令牌，恢复点比对令牌 + 把 `closing`/quiesced 与终态同列为中止条件；中止时对续体本地已取得的 lease/session 显式回收（close/release），不依赖字段回读。
2. cleanup/close 在**排队时**捕获 {epoch, session, lease, unsubscribe} 所有权，执行期仅处置捕获对象；`closeSessionAndRelease` 的退订改为只退捕获句柄（删除入口无条件 `quiesceSync` 对当前字段的操作）。
3. `removeTarget` 校验 `CLOSE_NAMESPACE` 返回序 >0 才武装 CLOSE_OK 等待，否则本地收口立即 settle；`onCloseOk` 错配改按库内既有 ACK 关联策略显式收口（fatal/ERROR），不做静默忽略。
4. `onConnectionLost` 各分支补全 timer 清理与 watchdog/round/channel/ACK-timer 的同步停摆；GOAWAY 收到同步段先静默订阅/停新 round，deadline 仅关 transport。
5. SA1 裁决生命周期权威归一：单一队列（或明确分工的单一抽象）收编 hub closeQueue 与 peer Memoized/cleanupTail/gate，同时清理 `isGoawayDraining` 死 seam。
