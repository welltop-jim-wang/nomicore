关键决策（带依据）：

- **D1 关联键 = 既有 wire sequence**（帧级）：protocol §3 envelope `sequence`（uint32，per-direction 严格递增）+ §10.2 `UPDATE_ACK.ackedSequence` 已构成闭环；SA5 §6 实测逐位配对成功，且证实按时间/字节长度猜关联在贪心合并下结构性失效。**零 wire 字节变更**（G3）。
- **D2 槽内样本经 apply 结果导出**：`RuntimeReplicationSessionApplyResult` ok 分支新增可选只读 `stages` 字段——每笔 apply 的结果即该笔样本的载体，**相关联天然精确**（无跨流配对）。这是冲突报告注记 4「槽内阶段的时差样本须经 session/内部 seam 结构化导出」的落点；发射仍在 ws-replication apply 结算续体（§23.4「永不位于 Registry write sequencer 槽内」）。
- **D3 单调时钟经 registry 构造选项注入 runtime**：namespace-runtime 现无任何时钟（grep 证实）；`@nomicore/clock` 只有可跳变 epoch 时源（`system.ts` = `Date.now()`）。§23.4/ADR-0009 禁止 epoch 时源作差 → 生产组合根注入**同一**单调实例给 ws-replication `clock?` 与 registry 新选项（守恒恒等式 §4.3 因此成立于同一时钟域）；缺省 dormant。装配期对缺省做响亮断言沿 issue #164 双层纪律（建议项，非本 repo 强制）。
- **D4 event-loop 探针锚定 liveness ping 周期**：不新增常驻 timer（无 observer 时零调度，逐字节等价）；cadence = `pingIntervalMs`（缺省 30 s，defaults.ts:41）；transport 无 ping/pong 面 → 探针 dormant（liveness.ts:5 既有缺面纪律）。
- **D5 槽级记账走 sequencer 私有标签 + 槽后 flush**：`sequencer.ts` 为包内零导出模块（L23「模块零导出」），`enqueue(run, label?)` 加性参不触 FIFO 核心；样本槽内只入缓冲数组（O(1) push，有界环），槽释放后续体投递——**槽内绝不调用外部回调**（同步回调会占用槽本身，恰是本议题要消除的病理形态）。
- **D6 发送侧分段以 `sendQueueMs` 补齐**：update-channel 既有 `sentAt` 出队记账（update-channel.ts:235）+ 新增 per-item 入队戳 → `update-sent.sendQueueMs` = 帧出队 − 帧内最旧项入队（发送方进程内精确）。ACK/回程段不新增字段：`ackLatencyMs − applyLatencyMs` 的跨进程减法只能作 triage 近似（两进程单调时钟域无共同零点），设计明示该边界（§5.3）。
- **D7 dormant 等价规则**：无 observer → 零事件/零探针调度；无 stageClock → 零槽内时钟读、`stages` 缺席、槽级记账关闭；clock throw → safeNow 折叠为字段缺席（§23.4 SA4 B1 同款），绝不外溢协议状态/unhandledRejection。
- **D8 修复腿不在本设计内预写任何「优化」**：在树管线无契约违背可修（§8.1 审计结论）；无证据的槽序/判据改动正是 G1/G2 演进门。修复腿 = 审计清单 + 契约回归测试 + 证据决策树（每支路的修复工项与各自门禁已预先登记）。

### 3.4 事件字段总表（protocol §23 修订的落点）

| 事件 | 新字段 | 在场条件 | 语义 |
|---|---|---|---|
| `update-sent` | `sequence: number` | 恒（事件发射即有） | 出站帧 envelope sequence（合并帧 = 该合并帧的 sequence；与既有 `bytes` 合并后长度口径同帧级） |

### 4.1 阶段定义与捕获锚点（peer 侧；hub 侧镜像）

| 段 | 字段 | 定义（差值） | 捕获点（HEAD `9e3f0bf` 锚） |
|---|---|---|---|
| sequencer queue wait | `queueWaitMs` | slotStart − admission | admission：replication-session.ts A4 `host.sequencer.enqueue(...)` 调用前（:487 邻域）；slotStart：`runSessionApplySlot` thunk 入口（:558） |

设计裁决：R1–R3（fatal/identity/writable 门）为 O(1) 同步投影读，并入 `protectedCheckMs` 而非单列——保住 Owner 四段词汇与字段经济性；H3 判别信号（scratch clone O(doc)）由 R4 主导该段，R1–R3 噪声可忽略（§8 决策树的判别阈值按此标注）。SA5 §5 的 `checkAndApply（R1–R5）` 验证口径与本定义兼容（其分解中该段 = 本设计的 protectedCheck+liveApply 之和）。

### 4.2 捕获纪律（红线逐条落实）

- **槽内只捕获，槽外发射**：四个戳 = 纯同步时钟读，零新增 await/调度；事件发射在 ws-replication apply 结算续体（peer-namespace.ts :1065-1079 既有续体）——§23.4「发射点永不位于 Registry write sequencer 槽内」+ 冲突报告红线 1。
- **无 stageClock → 零时钟读**（dormant；「无 observer = 零事件、零状态投影读取、零时钟调用」在 runtime 层的对应物：无注入即零采样）。
- **clock throw → 折叠**：safe-read 包裹，任一读 throw → 整个 `stages` 缺席；不产生 unhandledRejection、不影响协议状态（§23.4 SA4 B1 同款纪律）。
- **refusal/fatal 路径**：ok:false 分支与 `RuntimeWriteFatalError` rejection 形状逐字节不动，无 `stages`（这些路径本就无 apply 成功事件）。
- **degraded bypass**：R4–R6 照跑（bypass 只改 R3 放行），`stages` 在结果中在场；但 `degraded-bypass-applied` 事件按既有纪律不携时延字段（§3.4）。

### 4.3 守恒恒等式（测试断言基础）

`queueWaitMs + protectedCheckMs + liveApplyMs + dirtyNotifyMs = dirtyDone − admission ≤ applyLatencyMs（= t1 − t0，t0 在 `session.applyRemoteUpdate` 调用前采样，peer-namespace.ts:1042）`

- 手动时钟测试域：微任务跳不推进时钟 → **逐笔相等**（SA5 §5 已以测试侧 seam 实证同一恒等式；新测试以生产 seam 复证）。
- 生产单调时钟域：右端残余 = t0→admission 同步段 + R7→结算续体微任务跳，亚毫秒量级；断言用 `sum ≤ applyLatencyMs` 且 `applyLatencyMs − sum < ε`（ε 取 50 ms，容纳宿主调度粒度）。
- 前提：ws-replication `clock` 与 registry `stageClock` 为**同一实例**（D3；组装纪律写入 §3.4 文档与 driver 用例）。

## 5. sent/applied/acked 关联设计（R4）

### 5.1 关联键与配对规则

- 键 = **帧级 wire sequence**（per-direction、连接局部、uint32 严格递增，protocol §3 L56-57；不跨连接、不持久化——ADR-0010 L213 非目标「跨重连 update ID 表」据此保持）。
- 配对：`update-sent{sequence}` ↔（对端 apply）`update-applied{sequence}` ↔（ACK 回程）`update-acked{sequence = ackedSequence}`（§10.2 L279）。零新增 wire 字段（G3 放行基础）。
- **合并帧语义**（结构性事实，必须文档化）：update-channel §5 贪心合并（update-channel.ts:254/296）下 N 笔业务 update 合并为一帧、共享一个 sequence——关联粒度 = **wire 帧**，不是业务写。`bytes` 字段既有口径（合并帧报合并后长度）与之自洽；ACK 的 sequence 覆盖整个合并帧载荷。按字节长度/时间猜关联在合并发生时失效（SA5 §6 实证）——sequence 是唯一稳定键，本设计使其在三事件面全程可见。

### 5.2 实现落点（零 wire 改动的纯 local 变更）

发送侧 `sequence` 在 `sendUpdateFrame` 的 `seq`（peer-namespace.ts:978 / hub-namespace.ts 镜像）与 channel `inFlight` 记账键（update-channel.ts:66/:236）已天然在场；接收侧 `onHubUpdate(message.sequence)`（peer-namespace.ts:536）/ hub `onUpdate(message.sequence)`（hub-namespace.ts:579）已传入 apply 管线（:1036/:857）；ACK 侧 `onAck(message.ackedSequence)`（:558）→ `onUpdateAcked` info 加性扩展。**全部为把已在域的值放进事件对象**。

### 5.3 跨进程边界的诚实声明（防止过度声明）

hub 与 peer 是不同进程，两处单调时钟**无共同零点**：`ackLatencyMs − applyLatencyMs` 之类的跨侧减法只可作 triage 近似（Issue 正文表格的用法即此类），不得宣称精确段值。精确分段只在进程内成立：发送方进程（`sendQueueMs`、`ackLatencyMs`）、接收方进程（四段 + `applyLatencyMs`）；跨侧由 sequence 做**逻辑**连接。回程/ACK 派发段无 wire 时间戳（G3 禁止），以「sender `ackLatencyMs` − receiver 各段之和」的近似残差覆盖（SA5 生产再推导示 ~156 ms@max 量级）。

### 5.4 发送侧补充分段（Issue AC「sender dispatch」项）

`update-sent.sendQueueMs`（§3.4）区分「hub 发送队列等待」与「线上传输」：per-item `queuedAt` 入队戳（clock-gated）+ 出队构帧时刻。判读：`sendQueueMs` 低 + `ackLatencyMs` 高 → 延迟不在发送方（与生产观测一致：Hub 侧健康）。

## 6. event-loop stall 判别探针（H1）

- **定义**：`delayMs = timer 实际 fire 时刻 − 计划 fire 时刻`（同一注入单调时钟域）。事件循环被同步长任务阻塞时，一切到期 timer 的 fire 统一后延——`delayMs` 是该窗口内 event-loop 停摆的**下界信号**（含 timer 后端粒度噪声；文档明示为判别探针而非精确测量）。
- **锚点**：liveness ping 周期（liveness.ts 既有 `pingHandle` 调度；`pingIntervalMs` 缺省 30 s，defaults.ts:41——生产 cadence 30 s/样本，低频，符合 §23.6 采样纪律）。不新增常驻 timer。
- **gating**：observer + clock + transport 提供 `ping`/`onPong`（liveness.ts:5 缺面 dormant 先例）三者齐备才武装；任一缺席 → 零状态、零调度（D7 等价）。
- **判别语义**（SA5 §7.2 H1 预测的形式化）：H1 为因 ⟺ 事故窗 `event-loop-delay-sampled.delayMs` 抬升 **且** 各同步段（protectedCheck/liveApply/dirty + ACK 派发间隔）同步膨胀；与 H4（仅 queueWait 膨胀、自身各段低）互斥可分。
- **边界**：fake-duplex 测试 harness 结构性排除 stall（SA5 §11.2）——本探针的测试为「手动时钟 + fake timer 注入已知漂移 → delayMs 精确复现」的正向控制，生产判别力依赖部署后数据。

## 7. sequencer 槽级记账（H4 判别；log/metrics/trace 域）

- **样本形状**：`{ namespaceId; slotKind: 'P0'|'S'|'E'|'R'|'schema'|'bump'|'close-barrier'; waitMs?: number; runMs: number; queueDepthAtStart: number }`（差值/计数；无绝对时间戳）。`waitMs` = 该槽自身入队→开跑（对 S 槽即业务写在 FIFO 中的排队）；`runMs` = 槽执行全程。
- **机制**：`WriteSequencer.enqueue(run, label?)`（sequencer.ts 包内私有模块，零公共导出——加性参不触 FIFO）；深度计数私有；样本槽内 push 入**有界环形缓冲**（容量 1024，满则丢最旧并计 drop——绝不无界增长）；**槽释放后续体** flush 给 sink。sink 由 registry 构造时以闭包盖 `namespaceId` 戳（§3.2）。无 `slotMetrics` sink → 整条记账关闭（零开销）。
- **落点纪律**：ADR-0008 L101「队列进度和内部事件属于日志、metrics 与 trace」——样本只进注入的 metrics/log sink；**不进** `NamespaceRuntime.getStatus()`（`replication` 两态域冻结，#132 修订 5）也不进 `ReplicationSession.getStatus()`（O-11 十一字段冻结）——G4。
- **判别语义**：事故窗 UPDATE 的 `queueWaitMs` 高 + 槽级样本显示同 namespace 长 `S`（或 `E`）槽 `runMs` → H4 成立（#237 成本域）；与 H1（探针抬升 + 各段同步膨胀）互斥可分。
- **红线**：sink 为同步回调但在**槽外**续体调用；sink throw 自捕获计数（沿 ADR-0007 L54「记录」面先例），绝不反哺槽内。

## 11. 测试触发考虑（红灯策略与命令）

### 11.1 基线保留（R1）

`ws-replication-issue238-repro.test.ts` 与 driver `hubClock/peerClock` dormant seam **字节不动**——Owner 登记值 `[5000,4000,3000,2000,1000]` 的锚不可漂移。新能力全部走新文件与新可选注入。

### 11.2 新红灯契约（实现前红、实现后绿）

新文件 `ws-replication-issue238-segmented-observation.test.ts`（driver 扩展：同一手动单调时钟实例同时注入 ws-replication `clock` 与 registry `replicationObservability.stageClock`）：

1. **四段分解**：saveGate 构型下逐笔断言 `queueWait/protectedCheck/liveApply/dirtyNotify` = SA5 §5 表值（u1 dirty=5000；u2–u5 queueWait=[4000,3000,2000,1000]；check/apply 段 0）。
2. **守恒**：逐笔 `sum(stages) === applyLatencyMs`（手动时钟精确相等）。
3. **sequence 关联**：非合并构型逐帧 `update-sent.sequence === update-applied.sequence === update-acked.sequence`，与发送侧记账 sequence 逐位相等；合并构型（压缩 inFlight 窗口诱发合并）断言一 sequence 覆盖合并帧、三事件计数一致。
4. **dormant 等价**：无 stageClock → 事件无四段字段（字段缺席断言）；无 observer → 零事件（既有模式复用）。
5. **clock-throw 折叠**：注入 throw 时钟 → 四段缺席、协议路径正常、零 unhandledRejection。
6. **wire 字节全等**：observer+clock 在场/缺席两构型的双向帧字节序列全等（conformance 既有模式扩展）。
7. **探针正向控制**：fake timer 注入已知漂移（计划 t、实际 t+Δ）→ `event-loop-delay-sampled.delayMs === Δ`；无 observer → 零探针调度断言。
8. **槽级记账**：门闩 + 一笔慢业务写（mutateData 经 gated persistence）→ 槽样本含长 `S` 槽 `runMs`、后续 R 槽 `waitMs` 抬升、`queueDepthAtStart` 正确；sink 不在场 → 零开销路径无样本无缓冲增长。
9. **throw 隔离**：observer 每事件 throw → 帧序列/终态/apply 结算与无 observer 基线全等（§23.7 既有用例扩展到新字段）。

| G2 受保护判据/成本优化（增量式 R4 检查） | **否** | R4 `protectedContentEvaluated` 判据零改动，仅计时；H3 修复支路明示须先评审 + ADR-0010 修订节（§8.2） |
| G3 wire 变更（新帧/字段/ACK 扩展） | **否** | 关联与分段全部 local seam；wire 字节全等断言入契约（§11.2-6） |
| G4 冻结公共面扩形（O-11 十一字段、replication 两态域、拒绝码闭集等注册表） | **否** | 两处 getStatus 零改动；拒绝码闭集零改动；lease open 2 键校验零改动；runtime 十二键零改动 |

**结论：不需要冲突门禁重跑。** 依据：本设计全部变更 = ① §23 自我声明的 append-only 事件面扩展（Issue AC 第 7 项明文要求的协议文档演进方式）；② 两个包间结果联合的**加性可选字段**（非任何冻结注册表成员；`Equal<>` 镜像锁由编译器强制保持）；③ 包内私有 seam（sequencer label、host 可选项）与 internal subpath 加性参（非公共 API）；④ 测试/文档。无 ADR 决策面（决策、槽序、判据、状态形状、wire）变更。

## 14. 风险与开放问题

1. **组装纪律依赖**：守恒恒等式与跨 seam 一致性要求 ws-replication `clock` 与 registry `stageClock` 为同一实例——纯约定，无法在库层强制。缓解：driver/测试断言同实例；文档 + 装配期响亮断言建议（issue #164 先例）；两实例不同时最坏后果 = 守恒断言失败/段值不可比，**不影响协议行为**（观测面故障不外溢，§23.4 同纪律）。
2. **event-loop 探针的噪声下界性**：`delayMs` 含 timer 后端粒度；判别依赖「多窗口对比 + 与各段膨胀的相关性」，非单样本定论（§6 已明示）。
3. **合并帧粒度**：关联粒度 = wire 帧；若生产需要业务写级关联，须 ACK 回带扩展或 out-of-band 记账——均触 G3/非目标，明示不做。
4. **跨侧减法的近似性**：§5.3 已声明；任何文档/结论不得把 `ack − apply` 跨侧差表述为精确段值。
5. **槽样本缓冲容量**：1024 环形 + drop 计数为实现期冻结常量（沿 FANOUT_CHANNEL_QUEUE_CAPACITY=16 的「冻结常量非配置」纪律，具体数值实现期定）；sink 慢速消费不阻塞槽（槽外投递）。
6. **liveness 缺面 transport 无探针**：生产 WS 提供 ping/pong（liveness 既有前提）；fake transport 测试以显式 ping/onPong 面注入（测试域扩展）。
7. **基线与新契约的双文件维护**：repro（测试侧 saveDoc 包覆）与分段测试（生产 seam）短期并存；前者是 Owner 登记锚不得改，后者稳定后可在后续任务评估合并——本设计不合并（R1 优先）。

## 15. 实现顺序建议（SA3 输入）

1. namespace-runtime：`stages` 类型 + host 可选项 + 槽内四戳 + sequencer label/缓冲（含包内测试：分段值、dormant 等价、clock-throw 折叠）→ 包 typecheck/test。
2. namespace-registry：options 透传 + namespaceId 包装 + 结果联合镜像（`Equal<>` 保持绿）→ 包 typecheck/test（含 lease 2 键校验、O-11、十二键负向守卫零改动通过）。
3. ws-replication：types 事件字段 + 三事件面 sequence + stages 发射 + sendQueueMs + onAck info 扩展（peer/hub 镜像）→ 聚焦测试。
4. liveness 探针 + 第 21 事件型 + dormant 断言。
5. driver/testing 面透传 + 新红灯契约文件（§11.2 全项）+ conformance 白名单同步扩。
6. protocol §23 修订（§3.4 总表逐条落 doc）+ watch item 1 的 ADR-0010 修订节一行登记。
7. 根门：`pnpm typecheck && pnpm test`；10×/20× 稳定性循环；Owner 复现命令回归（基线零改动验证）。

## 结论

- 设计以**零 wire 变更、零槽序变更、零判据变更、零冻结注册表扩形**（G1–G4 逐门核验通过，§13）实现 Owner 的四段观测 + 帧级 sent/applied/acked 关联：四段差值经 apply 结果加性字段从唯一合法导出点（session/内部 seam）离开槽，事件发射留在 apply 结算续体；关联键复用既有 wire sequence；event-loop 与槽级记账补齐 H1/H4 判别面；修复腿按证据决策树闭合，不预写无证据「优化」。
- 基线复现的 clock/gate 性质按 Owner 要求原样保留，其「机制证明、非生产阶段证明」的边界在设计内一贯保持（R1/R2）。
- 冲突复核结论：**不需要重跑**（无 ADR/protocol 决策面变更；§23 演进走其自身 append-only 条款；watch items 已登记）。

Verdict: approve（设计达成 Owner 要求与 Issue AC 的可实现映射；红线与边界逐条落实）
