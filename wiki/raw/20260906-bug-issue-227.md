### 2.2 sweep 侧两处洞（G2）

- 判定点一次性检查：P1 年龄遍历 `segmentLeased(...)`（file.ts:1226）、P2 字节遍历（:1281）之后经历
  `groupAgeExpired`（整文件 readFileSync）/`groupBytesBeforeDelete`（两次 statSync）等 IO，才到
  `deleteGroup` 的 S1 `renameSync(jsonl→.deleting)`（:1071）——「检查→提交」之间无复查门（结构性 TOCTOU 面；
  单线程同步下今日靠调度事实隐式安全，AC2 要求升格为结构保证）。
- P0 卫生遍历完全无租约门：`hygieneStream` 的 orphan-BIN 清理（:1134–1151）对「闭组 ∧ jsonl 缺 ∧ marker 缺 ∧
  bin 在」直接 `unlinkSync(binPath)`（:1145–1150），**没有任何 `segmentLeased` 调用**——这是可动态复现的
  实际删除违约（见 Leg D：活跃租约下 bin 仍被删）。

### 2.3 replay 完整性判定洞（G3/G4/F-1）

- 判定链：`committed = kind==='committed' || (kind==='fatal' && committed===true)`（diagnostic-replay.ts:171）→
  `hasUpdateCarrier = committed && effect==='update' && update 形状合法`（:183–188，**先形状后必要性**）→
  false 时 `else if (genesisSeen)` 推进 `lastSeq/expectedNext`（:208–212）。
- `fatal/committed:true/effect:'unknown'`（schema.ts:181 第 8 成员，emitter 可达——pipeline.ts:118/:145）与
  `fatal/committed:true`（effect 字段缺席，schema.ts:178 第 5 成员，emitter 不可达、盘面可达）两形状都落
  `hasUpdateCarrier=false` → 推进。
- 包级同病：`materializeStrictRecordUpdate`（reader.ts:777–824）attempt 分支对上述两形状落兜底
  `return {kind:'none'}`（:817）——「不可证必要性」与「可证无更新（noop/rejected/fatal-committed:false）」同归
  `none`，上层无从区分。
- complete 门 `issues===[] ∧ applied>0 ∧ readStatusOk ∧ !historyTrimmed`（:227–232）本身不坏；被穿透是因为
  必要性不可证的记录既不产 issue 也不中断。
- 既有 pin（须废止）：`apps/yjs-server/test/diagnostic-replay-host-lifecycle-sa7.test.ts:445–475`
  「健康链中段含 fatal-unknown 记录：complete、issues=[]、lastAppliedSequence '4'、快照复现终态」——
  本轮 vitest 实跑 6/6 绿（含该用例），Leg A 的 A4/A5 与其断言逐字一致。

### 2.4 G5 现状（防御面，非现行洞）

`committed ∧ effect:'update'` + `update` 字段畸形（如 `update:42`）：strict 逐行 VFSL 校验
（reader.ts:610–626）即拒 → `entry.ok=false` + record 级 `vfsl-invalid` → replay 停止（Leg C 实测
`status=partial, issues=[vfsl-invalid, vfsl-invalid]`）。设计的 G5 修复（必要性先于形状判定）是次序加固，
防未来 schema 演进/第三方 writer 打开该面——SA6 的 D6 第二断言按「非 complete」写即可（今日已满足）。
